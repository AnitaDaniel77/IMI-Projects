Capstone Project - Reserve a Table Functionality

Exercise: Connecting to the Booking API

Scenario

Without real availability data, two customers could book the same table at the same time - a genuinely bad experience. This exercise wires the booking form up to an actual API so availableTimes reflects real, current bookings instead of a hardcoded placeholder list.

Step 1 - The API's two functions

  • fetchAPI(date) - takes a date, returns an array of available times for that date
  • submitAPI(formData) - takes the booking form data, returns true if submission succeeded

These come from a script tag added to index.html, which the course provides separately (a small standalone JS file exposing these two functions globally).

Step 2 - Updating initializeTimes and updateTimes

export function initializeTimes() {
  const today = new Date();
  // fetchAPI comes from the script loaded in index.html - it's
  // a GLOBAL function, not something imported like a normal module
  return fetchAPI(today);
}

export function updateTimes(state, action) {
  switch (action.type) {
    case 'date_change':
      // the date dispatched from BookingForm gets passed straight
      // into fetchAPI, so times actually change based on selection
      return fetchAPI(new Date(action.date));
    default:
      return state;
  }
}

Real-life example: this is like a restaurant host checking a live reservation book instead of reciting a memorized, fixed list of open tables - the moment a date changes, the host looks up that specific day's real availability instead of repeating the same answer regardless of what was asked.

Step 3 - Verifying it works

Change the date in the form and confirm the time dropdown's options actually change - if they stay identical no matter what date is picked, the dispatch isn't reaching updateTimes correctly, or the reducer isn't calling fetchAPI with the new date.
