Defining Solutions

Course: Coding Interview Preparation — Module 1

Overview

Computer science lets us model and test scenarios virtually before committing real resources — testing a plane's flight, predicting weather, or solving any problem without building the physical thing first. Defining a solution properly has three stages: articulate the problem statement, formulate a model, then finetune the solution.

1. Problem statement

Start by articulating the problem in the shape: I need to achieve A, with tools T, given constraints C.

Example: designing an app to entertain a child with a guessing game. Before writing anything, work through:

  • How will the child interact with the computer?
  • What level of questions should be asked?
  • Where do the questions come from, and how are they stored?
  • How are answers checked?
  • How does the program start and end?

Also weigh hardware/software constraints — age-appropriate safety, internet reliability, device compatibility, target OS or browser.

Real-life analogy: it's like planning a road trip before checking the car has enough fuel, whether the roads are paved, and whether your phone will have signal — skipping this step means finding out the hard way, mid-journey.

2. Formulate a model

Once constraints are known, propose a model. For the guessing game: assume a computer-friendly-age child, laptop-only, local storage (no internet issues), keyboard input on the command line.

An algorithm is a precise sequence of instructions to solve a problem. Sketch it first as pseudocode — a text-based description of requirements — before touching real code:

Generate a question → take in user input → compare input with answer → return a result

From there, work through the specifics: where do questions come from (dynamically generated vs. a pre-compiled bank)? How is input compared — exact match, or accounting for spelling/punctuation/capitalization? Would multiple-choice sidestep the matching problem entirely?

3. Finetune the solution

Reflection can reshape the whole approach — here, a trivia format is dropped in favour of a simpler, more universal number-guessing game: no external sources needed, works in nearly any language.

Generate random number → take input, store in variable → compare input with answer → return result

A flowchart of this pseudocode surfaces further questions:

  • Does the program run once, or does it offer another guess after a wrong answer?
  • Should the user get steering prompts ("too high"/"too low") instead of a flat failure message?
  • What happens if the user enters a non-number?

Working through these systematically — before implementation — is what catches issues early and can even change the scope of the whole project (e.g. shifting from "build the game for the child" to "build a framework so the child can build their own game").

Key takeaway

Problem statement → model → finetuning is a repeatable habit, not a one-off exercise. It applies as much to a professional application as to a toy project, and it's worth establishing early rather than skipping straight to code.

Pseudocode tip

Pseudocode is written as plain-language steps, not language syntax — it should read like a recipe, not code. Write it before touching an IDE: it forces you to spot missing logic (like the "what if input isn't a number?" case) while it's still cheap to fix.
