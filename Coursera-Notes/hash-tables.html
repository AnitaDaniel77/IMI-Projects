Hash Tables

Course: Coding Interview Preparation — Module 2

What a hash table is

A structure of slots/buckets holding key-value pairs. A hashing function — any algorithm that reduces a key to a fixed-size, unique-ish number — decides which bucket a value goes into.

Real-life analogy: like compressing a file before sending it over the internet, then decompressing on the other end — hashing reduces a key to a small, manageable size that acts as an index.

What gets hashed depends on the application — could be the raw data itself, the last four digits of an ID number, or a dictionary key. Most languages have built-in hash functions (MD5, SHA, CRC32), so implementing one is usually straightforward.

Why hash tables are fast

Big-O trade-off: speed vs. space. Hash tables prioritize speed, retrieving items in O(1) time.

Compare to an array search: checking whether a value exists means comparing against every element — worst case O(n), if the value's at the end (or absent). A hash table skips this by mapping a key directly to its storage location via the hash function, so a lookup just recomputes the hash and goes straight there — like using a book's index instead of reading page by page.

Common uses: caches, dictionaries, database indexes, sets.

Worked example

10 keys (0-9), hashing function = modulus 20:

0 mod 20 = 0
1 mod 20 = 1
2 mod 20 = 2
...

Each key maps to a unique slot — simple, but illustrates the mechanism. Problem: once key count exceeds 20, collisions start (e.g. 1 mod 20 = 1, and 21 mod 20 also = 1).

Collisions and the birthday paradox

A collision is when two different keys hash to the same value. Counter-intuitively likely to happen sooner than expected — the birthday paradox: in a random group of just 23 people, there's roughly a 50% chance two share a birthday. Applied to hashing: 24 employees hashed by birthday into 365 slots still has a >50% chance of a collision, despite 365 looking like plenty of room.

Handling collisions

  • Grow the table: when a collision occurs, expand the table and increase hashing complexity, redistributing values to new slots — the table grows organically to match data size.
  • Chaining: store a linked list at the collision point instead of a single value — multiple values share a slot without overwriting each other.

Key takeaway

Hash tables trade some space/complexity for near-instant O(1) lookups. Collisions aren't a rare edge case — they're a near-certainty at scale, so any real implementation needs a collision strategy (table growth or chaining) built in from the start.
