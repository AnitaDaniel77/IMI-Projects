Objects

Course: Coding Interview Preparation — Module 2

What an object is

A structure with both state and behavior. State (attributes) is the information the object holds — a person's age or name. Behavior is what the object can do — calling a method, like sorting an array or a person running.

Class: the blueprint. Object: an instance of that class.

Why objects — reusability

One class template can produce many independent instances. A football team needs only one Player class, then 11 separate objects with different speed, agility, and work rate — massively cutting code overhead versus writing each player from scratch.

Instance variables and independence

Player player1 = new Player(agility = 54, speed = 88, fitness = 90);
Player player2 = new Player(agility = 90, speed = 64, fitness = 83);

These characteristics (speed, agility, fitness) are instance variables — part of that object's own state, invisible to and unaffected by other instances. Changing player1's fitness never touches player2's.

Getters and setters

player1.set_fitness(80)

Methods that change an attribute's value are called setters (and getters retrieve them). This only alters player1 — other objects are untouched.

Behavior via methods

player1.kick()

Calling a method makes that specific object perform an action — here, only player1 kicks.

Inheritance

Need a referee who shares some traits with players (running, general appearance) but isn't a player? Create a shared Human class holding the common attributes/methods, and let Player and Referee both inherit from it — avoiding duplicated code for behavior they genuinely share.

Real-life analogy: think of "Human" as a shared employee handbook — both "Player" and "Referee" follow the same base rules (how to walk onto the pitch, general conduct), but each role also has its own specific duties layered on top.

Polymorphism

One general concept manifesting in different forms. "Human" → Player, Referee, Manager, each with their own specifics. Classic example: a Shape class defining area, diameter, height conceptually — then Square, Triangle, Circle each implement those concepts differently for their own shape.

This directly echoes the PaymentMethod interface pattern from Capstone 2 — one shared contract (Shape / PaymentMethod), multiple concrete implementations (Square, Circle / CardPayment, EftPayment) each doing their own version of the same behavior.

Key takeaway

Objects package state and behavior together. Classes define the blueprint once; objects are independent instances of it. Inheritance shares common structure; polymorphism lets one shared concept take multiple concrete forms — the same idea already put into practice with PaymentMethod's Card/EFT/Wallet implementations.
