Reading: Recap - Unit Testing

Manual testing (clicking through the app in a browser to check everything by hand) is slow and error-prone. Unit testing, automated testing, and integration testing are the usual alternatives - this reading focuses on unit testing specifically.

What unit testing actually tests

Unit testing focuses on individual units of code - in a React app, that usually means testing one component at a time in isolation.

Real-life example: unit testing a single component is like a chef tasting one sauce on its own before plating the whole dish - checking that this one piece works correctly by itself, before worrying about how it combines with everything else.

A simple counter component

function App() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </div>
  );
}

Writing the test (App.test.js)

import { render, screen, fireEvent } from '@testing-library/react';
import App from './App';

test('increments count on button click', () => {
  render(<App />);
  // renders the component into a virtual DOM for testing, without
  // needing an actual browser open

  const button = screen.getByText('Increment');
  // finds the button the same way a real user would - by its
  // visible text, not by some internal implementation detail

  fireEvent.click(button);
  // simulates an actual click event, same as a user clicking it

  expect(screen.getByText('1')).toBeInTheDocument();
  // checks that "1" now appears on the screen after the click
});

Real-life example: fireEvent.click is like a mystery shopper actually pressing a button in a store, rather than an inspector opening up the till and checking the wiring directly - the test behaves like a real user would, not like it's peeking at internals.

Running tests

npm test
# or
npm run test
# both commands do the same thing - watches for file changes and
# re-runs relevant tests automatically

Best practices

  • Avoid testing implementation details - test what the user sees/does, not internal variable names or state structure
  • Work with DOM nodes - query by what's visibly rendered (text, labels, roles), not by digging into component internals
  • Resemble software usage - write tests the way a real user would interact with the app
  • Keep maintainability in mind - tests that break on every small refactor become a burden rather than a safety net

Real-life example: "avoid implementation details" is like a driving test checking whether you can actually drive safely, not whether you know the exact wiring diagram of the car's engine - what matters is the behavior that's visible and real, not the internals underneath.
