Coding Interview Preparation

Reading: Testing Your Solution

Testing tends to get pushed to the end and cut when deadlines loom - Test Driven Development (TDD) exists specifically to avoid that pattern. Two contexts covered here: take-home assignments and live coding interviews.

Take-home assignment - more time, more test types available

  • Integration tests - how different components interact with each other; external dependencies get simulated rather than using real instances. Broader/more global than unit tests, which check individual lines of code.
  • Functional tests - automated proof that the system behaves as expected, focused on capability.
  • Regression tests - confirm a new change hasn't broken existing, already-working code.

Real-life example: integration tests are like checking that a car's engine, brakes, and steering all work together on a test drive, while unit tests are like checking each individual part (the brake pads, the spark plugs) in isolation on a bench first.

How much testing actually fits depends on time available - a genuinely working application matters most, and thorough testing is what demonstrates real thoroughness on top of that.

Coding interview - unit testing specifically

There's no time to write a full test suite live in an interview, but incorporating unit tests where possible demonstrates real attention to detail and good practice - even a small amount is a meaningful signal.

Unit tests check individual components work as expected, rather than the whole system's overall behavior.

Three things to actually consider when writing tests

  • Readability - tests should be clear to other developers (and to yourself later) - a test with an obvious purpose helps pinpoint a problem quickly and effectively documents what a piece of code is supposed to do
  • Clear/deterministic outcomes - a test should return the same result every time given the same conditions; a test that only fails under some combination of conditions is much harder to debug
  • Automation potential - tests should be runnable quickly and repeatedly whenever code changes - this is the actual foundation CI/CD pipelines are built on

Worked example - a number-guessing game

Pseudocode:
1. Generate a random number
2. Take in user input, store in a variable
3. Compare input with the answer
4. Return the result

With only a few minutes left in an interview, the priority becomes the most basic tests: assert-based cases confirming that given input produces expected output. Most languages have a built-in or standard library for this.

assert isinstance(user_input, int), "Input should be an integer"
assert 1 <= user_input <= 100, "Input should be within the valid range"
# checking the RANDOM NUMBER is valid matters just as much as
# checking user input - a bug in generation is just as real a
# bug as a bug in validation
assert isinstance(random_number, int)
assert 1 <= random_number <= 100

Priority order under time pressure, in this example:

  1. User input validation first - was something actually entered, is it the correct type, does it avoid crashing the program, is it within bounds
  2. Random number validation second - correct type, within acceptable range
  3. Conditional outcome checks last - confirming the right result fires when the comparison logic runs

Real-life example: prioritizing input validation first is like checking a delivery address is even valid before worrying about how fast the delivery truck can drive - garbage input makes everything downstream meaningless, no matter how well the rest works.

Why this matters for how you're perceived

Writing tests is often marginalized in favor of just implementing the solution. The practical fix: write tests as you go, not after. Even quick unit tests under time pressure signal real thoroughness and can genuinely strengthen how a candidate is perceived in an interview.
