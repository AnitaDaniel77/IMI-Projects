Introduction to Databases

Acronyms

  • SQL: Structured Query Language, used to read and change data in relational databases.
  • NoSQL: "Not only SQL", databases that don't use fixed tables.
  • IoT: Internet of Things, devices like smart meters and sensors that send data over the internet.

What a database is

An organised collection of data that's stored and managed electronically. It's built so you can quickly find one record or analyse millions.

Real-life example: a digital filing cabinet. Capitec stores every client, account and transaction in one, so your balance shows up the moment you open the app.

Why not just use files?

Files work for small apps but get slow and error-prone as data grows. Databases give you:

  • Efficient retrieval: they're built to find specific data fast, even in huge datasets.
  • Data integrity: data stays accurate and consistent, even with many users at once.
  • Scalability: they handle more data as the app grows.
  • Security: built-in access control and protection for sensitive data.

Real-life example: keeping client records in one Excel file works for a single branch. Once there are 900 branches and millions of clients updating at the same time, you need a database.

Types of databases

  • Relational: tables with rows and columns, linked to each other and queried with SQL. Example: a Students table and an Enrolments table. Use it for structured data like inventory or accounts (MySQL).
  • NoSQL: flexible storage as key-value pairs, documents or graphs. Example: MongoDB for logs and user activity.
  • Graph: built for complex relationships, like social networks and recommendations (Netflix "because you watched").
  • Time series: timestamped data like server logs, stock prices or sensor readings (InfluxDB for a weather app).

Real-life example: client accounts belong in relational tables, the app's click logs suit NoSQL, a fraud ring of linked accounts suits a graph, and ATM cash levels every minute suit time series.

Transactions

A transaction is a group of steps that must all succeed together or not happen at all. If anything fails partway through, the database rolls back to how things were before.

Real-life example: a transfer takes money out of your account and puts it into your friend's. If the second step fails, the first is undone, so the money never just disappears.

Concurrent access

Many users can read and write at the same time without corrupting the data.

Real-life example: thousands of people buying concert tickets at once, and no seat gets sold twice.

Real-world uses

  • E-commerce: product catalogues, orders and payments (Amazon).
  • Healthcare: patient records and appointments.
  • Entertainment: shows and user preferences (Netflix).
  • Finance: accounts, transactions and fraud detection.

Pseudocode: a money transfer as a transaction


START transaction
    IF from-account balance is less than amount
        ROLLBACK, stop
    subtract amount from from-account
    add amount to to-account
    IF any step failed
        ROLLBACK (put everything back)
    ELSE
        COMMIT (make it permanent)

Tips for understanding the logic

  • Pick the database type by the shape of your data: fixed fields, flexible documents, relationships or timestamps.
  • Think of a transaction as all or nothing. There's no halfway state.
  • Commit means "save for real". Rollback means "undo everything since start".
