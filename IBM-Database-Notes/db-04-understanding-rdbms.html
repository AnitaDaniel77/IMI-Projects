Understanding RDBMS with Examples

Acronyms

  • RDBMS: Relational Database Management System, software that stores data in linked tables (MySQL, PostgreSQL, Oracle).
  • PK: Primary Key, the column that uniquely identifies each row.
  • FK: Foreign Key, a column that points to another table's primary key.
  • SQL: Structured Query Language.

Tables, rows and columns

An RDBMS stores data in tables, like a grid. Each row is one record, and each column is one field.

Real-life example: a client table where each row is one client and the columns are ID number, name, cellphone and branch.

Primary key

A column (or set of columns) that uniquely identifies each row. It stops duplicate records. Example: studentId.

Real-life example: your account number. No two clients share one.

Foreign key

A column in one table that points to the primary key of another table, which creates a relationship. Example: studentId in the Enrolments table points to the Students table. That way, student details aren't copied into every enrolment.

Real-life example: a transaction record stores your account number, not your whole name and address, and the account number links back to your full details.

Schema

The blueprint of the database: which tables exist, their columns and data types, the relationships between them, and constraints like PKs, FKs and validation rules.

Real-life example: the architect's plan of a branch, showing the rooms, what goes in each one and which doors connect them.

Normalisation

Splitting data into smaller, related tables to stop repetition and keep it accurate. Instead of typing "Databases" in every enrolment row, keep it once in a Courses table and store only the courseId in Enrolments.

Real-life example: if the branch name is typed into every client row and the branch gets renamed, you'd have to fix thousands of rows. With a separate Branch table, you change it once.

Index

Speeds up searches, like the index at the back of a book. Without one, the database checks every row (a full table scan). The trade-off is that inserts and updates get slightly slower, because the index has to be updated too.

Real-life example: finding a client by ID number in an indexed system is instant. Without the index, it's like flipping through every paper file in the branch.

Relationships

  • One-to-one: each person has one passport, and each passport belongs to one person.
  • One-to-many: one customer places many orders, and each order belongs to one customer.
  • Many-to-many: students take many courses, and courses have many students. This needs a join table (Enrolments) in the middle.

Real-life example: one client has many accounts (one-to-many). An account can have several signatories and a person can sign on several accounts (many-to-many, with a join table).

When to use RDBMS vs NoSQL

RDBMS suits structured data where relationships and accuracy matter: e-commerce orders, healthcare records and banking. NoSQL (MongoDB) suits unstructured or fast-changing, real-time data, but it doesn't have the strict structure and relationships.

Pseudocode: enrolling a student safely


ADD student
    IF studentId already exists -> reject (primary key)
    ELSE save row, update index

ENROLL(studentId, courseId)
    IF student not found OR course not found -> reject (foreign key)
    ELSE add row to enrolments join table

FIND courses for a student (like a JOIN)
    FOR each enrolment with this studentId
        look up the course by courseId
        print course title

Tips for understanding the logic

  • Ask "what makes this row unique?" That's your primary key.
  • Ask "does this column point somewhere else?" That's a foreign key.
  • If you see the same text repeated in many rows, normalise it into its own table.
  • Index the columns you search by most often, not every column.
  • A many-to-many relationship always needs a join table in the middle.
