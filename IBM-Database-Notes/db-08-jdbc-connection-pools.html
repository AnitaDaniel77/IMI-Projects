JDBC, Connections and Connection Pools

Acronyms

  • JDBC: Java Database Connectivity, Java's standard way to talk to relational databases.
  • API: Application Programming Interface, a set of classes and methods you call.
  • DBCP: Database Connection Pooling, Apache Commons' library for connection pools.
  • URL: here it means the database address, like jdbc:mysql://localhost:3306/shop.

What JDBC is

A standard Java API that lets your code connect to MySQL, PostgreSQL, Oracle and others, run SQL, and read the results. It's the bridge between Java and the database.

Real-life example: a translator between you and a client who speaks another language. You speak Java, the database speaks SQL, and JDBC passes the messages both ways.

JDBC architecture

  • DriverManager: keeps track of the drivers and opens connections.
  • Driver: the database-specific piece, like the MySQL driver or PostgreSQL driver.
  • Connection: the open line to the database, where everything starts.
  • Statement / PreparedStatement: carry your SQL to the database. PreparedStatement uses ? placeholders and is safer.
  • ResultSet: holds the rows that come back.

Flow: Java app, then JDBC API, then DriverManager, then the right Driver, then the database. Statement runs the SQL, and ResultSet brings the rows back.

Real-life example: DriverManager is the switchboard, the driver is the right phone line for that office, the connection is the call, the statement is what you say, and the ResultSet is their answer.

Connecting with JDBC

  1. Add the driver, for MySQL the mysql-connector-j dependency in pom.xml.
  2. Call DriverManager.getConnection(url, user, password) inside try-with-resources, so the connection closes itself even if there's an error.
  3. Catch SQLException, so a database problem doesn't crash the program.

The problem without a pool

If every request opens and closes its own connection:

  • High latency: opening a connection is slow, so every request waits.
  • Resource exhaustion: the database only allows so many connections, and it runs out.
  • Scalability issues: more users means more failures and lost sales.

Connection pooling

Open a set of connections up front. Each request borrows one and gives it back when done, so nobody opens a new one each time. You get better performance, use fewer resources, and can handle more users.

Real-life example: a branch has a few consultants on duty. Clients take the next free consultant, and when they're done that consultant helps the next client. You don't hire and fire a consultant for every client.

Apache Commons DBCP

  • BasicDataSource: the pool object.
  • setInitialSize: how many connections to open at startup.
  • setMaxTotal: the most connections allowed at once.
  • getConnection(): borrow one. Calling close() on it gives it back to the pool instead of really closing it.

Pool tips for real systems

  • Size it from traffic: for example, start at 50 and allow up to 200 at peak times.
  • Handle idle connections, timeouts and failures, so connections don't leak.
  • Monitor the pool and tune the settings as usage changes.

Spring Boot uses a pool called HikariCP by default, so you get pooling automatically there.

Pseudocode: borrowing from a pool


AT STARTUP
    open N connections, put them in the pool

WHEN a request comes in
    IF a free connection exists
        take it, run the SQL, read results
        give it back to the pool
    ELSE
        wait (or open a new one if under the max)

AT SHUTDOWN
    close every connection in the pool

Tips for understanding the logic

  • DriverManager gives you a brand-new connection each time. A pool gives you a recycled one.
  • With a pool, conn.close() means "give back", not "destroy".
  • Always use try-with-resources, or connections leak and the pool runs dry.
  • "No suitable driver" means the driver dependency is missing.
