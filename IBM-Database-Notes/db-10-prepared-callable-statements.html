Prepared and Callable Statements in JDBC

Acronyms

  • JDBC: Java Database Connectivity.
  • SQL injection: an attack where someone types SQL into an input box so your query does something you didn't intend.
  • IN / OUT parameter: IN sends a value into a stored procedure. OUT receives a value back from it.

Why not just Statement?

A plain Statement glues the values straight into the SQL text. That's open to SQL injection, and the database has to re-read the SQL every time, which is slower for repeated queries.

Injection example: if a name box gets the input ' OR '1'='1, a glued query becomes WHERE Author = '' OR '1'='1', which returns every row.

Real-life example: a teller who reads the client's form out loud and does whatever it says, including a scribbled "and give me the vault key".

PreparedStatement

The SQL has ? placeholders, and the values are filled in separately with setString, setDouble, setInt and so on. The number shows the position: 1 is the first ?, 2 is the second.

  • Prevents SQL injection, because values are treated as data, never as code.
  • Faster for repeats, because the database prepares and caches the query once.
  • Reusable: the same query with different values.

executeUpdate() is for INSERT, UPDATE and DELETE, and returns how many rows changed. executeQuery() is for SELECT and returns a ResultSet.

Real-life example: a printed form with blank boxes. The client can only fill in the boxes, they can't change the form's instructions.

Getting the generated key

When the ID is AUTO_INCREMENT, pass Statement.RETURN_GENERATED_KEYS to prepareStatement, then read getGeneratedKeys() after the insert. You need that new ID to link other records to it, like adding order items to a new order.

Real-life example: opening an account and immediately getting the new account number, so you can link a debit card to it.

CallableStatement

Calls a stored procedure using {CALL ProcedureName(?, ?)}.

  • IN parameters: set them with setString and similar, the same as PreparedStatement.
  • OUT parameters: tell JDBC the type first with registerOutParameter(2, Types.DOUBLE), run execute(), then read the value with getDouble(2).
  • If the procedure returns rows, use executeQuery() and loop through the ResultSet.

Real-life example: asking head office to run month-end interest. You hand over the account type (IN), and they hand back the total interest paid (OUT).

Statement vs PreparedStatement vs CallableStatement

  • Statement: fixed SQL with no user input. Simple, but unsafe with input.
  • PreparedStatement: any SQL with values. Safe, fast and reusable. This should be your default.
  • CallableStatement: running stored procedures, including OUT values.

Error handling

Use try-with-resources so statements and connections always close, and catch SQLException so a missing table or bad query shows a clear message instead of crashing the app.

Pseudocode: insert, then link


PREPARE "INSERT INTO Books (Title, Author, Price) VALUES (?, ?, ?)" asking for generated keys
SET 1 = title, 2 = author, 3 = price
RUN executeUpdate
READ generated key -> newId
PREPARE "UPDATE Books SET Price = ? WHERE BookID = ?"
SET 1 = new price, 2 = newId
RUN executeUpdate

Pseudocode: procedure with OUT


PREPARE CALL GetAveragePrice(?, ?)
SET IN 1 = author
REGISTER OUT 2 as DOUBLE
EXECUTE
READ OUT 2 -> average

Tips for understanding the logic

  • Count the question marks, and you should have the same number of set calls.
  • Placeholder numbers start at 1, not 0.
  • registerOutParameter must come before execute().
  • Never build SQL with + and user input. Always use ?.
