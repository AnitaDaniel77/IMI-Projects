Using JPA for Database Operations

Acronyms

  • JPA: Jakarta (formerly Java) Persistence API. It's a specification, a set of rules for saving Java objects to a database.
  • ORM: Object-Relational Mapping, turning table rows into Java objects and back.
  • JPQL: Java Persistence Query Language, queries written against classes and fields instead of tables and columns.
  • DDL: Data Definition Language (CREATE, ALTER). ddl-auto lets Hibernate run DDL for you.
  • Hibernate: the library that actually does the work JPA describes. JPA is the rulebook, Hibernate is the player.

What JPA is

JPA maps Java classes (entities) to database tables, so you work with objects instead of writing SQL and reading ResultSets by hand.

  • Abstraction over SQL: call save() instead of writing INSERT.
  • Entity management: JPA handles persisting, merging and deleting objects.
  • Simplified querying: JPQL, or method names that Spring turns into queries.

Real-life example: with JDBC you fill in every field of a paper form yourself. With JPA you hand over the client's file and the system captures it.

JDBC vs JPA

  • JDBC: you open connections, write SQL, set ? values, loop through the ResultSet and build the objects yourself. Lots of repeated code.
  • JPA: you describe the class with annotations, and the repository gives you save, findById, findAll and deleteById for free.
  • JDBC SQL is often tied to one database. JPA is database independent, so switching from MySQL to PostgreSQL is mostly a settings change.

Real-life example: JDBC is driving a manual car, where you control everything. JPA is an automatic, where you still steer but the gears are handled for you.

Why use it

  • Less boilerplate code.
  • Classes map straight to tables: a Book class maps to a books table.
  • Database independence.
  • Automatic schema management with ddl-auto.
  • Easier maintenance, because changes to the data model live in the entity class.
  • Built into Spring Boot through spring-boot-starter-data-jpa.

ddl-auto options

  • update: creates missing tables and columns, keeps the data. Good for development.
  • create: drops and recreates the tables on every start, which wipes all data.
  • validate: only checks the tables match the entities and fails if not. Safe for production.
  • none: does nothing. Use with proper migration tools in production.

Never use create or update on a live database. A wrong field rename could drop or change real data.

Setup steps

  1. Add spring-boot-starter-data-jpa and mysql-connector-j to pom.xml.
  2. Configure the datasource and JPA settings in application.properties.
  3. Define an entity: @Entity on the class, @Id on the primary key, and @GeneratedValue for how the ID is made.
  4. Create a repository: an interface that extends JpaRepository<Book, Long>, meaning the entity type and the ID type.

Best practices

  • Keep entities simple, with only the fields that belong in the table.
  • Use clear names that match the business (Book, title, author).
  • Use the built-in repository methods before writing custom queries.

Pseudocode: saving a book with JPA


CREATE new Book object
SET title, author, price
CALL repository.save(book)
    JPA builds the INSERT for you
    database creates the id
    id is copied back into the book object
CALL repository.findAll()
    JPA builds the SELECT and turns rows into Book objects

Tips for understanding the logic

  • You never write the repository class. Spring creates it at startup from the interface.
  • The <Book, Long> in JpaRepository must match the entity and its @Id type.
  • Turn on show-sql to see the exact SQL JPA runs. It's the best way to learn what's happening.
  • Entities need a no-argument constructor, because JPA creates the objects itself.
