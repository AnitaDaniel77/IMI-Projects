Setting Up a RESTful API for CRUD

Acronyms

  • REST: Representational State Transfer, a style for web APIs where each URL is a resource and HTTP methods say what to do with it.
  • API: Application Programming Interface, the endpoints other apps call.
  • CRUD: Create, Read, Update, Delete.
  • HTTP: HyperText Transfer Protocol.
  • JSON: JavaScript Object Notation, the text format the API sends back.
  • cURL: Client URL, a command-line tool for sending requests to an API.
  • SLF4J: Simple Logging Facade for Java. Logback is the engine behind it.

What a RESTful API is

Clients like browsers and mobile apps talk to the server using HTTP methods. Each method maps to a CRUD action:

  • GET: read data.
  • POST: create new data.
  • PUT: update existing data.
  • DELETE: remove data.

Spring Boot makes this quick: @RestController defines endpoints, JPA talks to the database without raw SQL, and validation checks input.

Real-life example: ordering food on an app. The app (client) sends your order to the restaurant's API, which saves it and sends back a confirmation.

Serialisation

Turning Java objects into JSON so they can travel over the network. Spring Boot does it automatically with the Jackson library.

Real-life example: packing a parcel into a standard box so any courier can carry it.

Structured responses

Instead of returning raw objects, wrap every response in an ApiResponse with three fields:

  • status: did it work (true or false).
  • message: a short description of what happened.
  • data: the actual payload, or null.

Every endpoint then answers in the same shape, which makes front-end code simpler.

Real-life example: a bank statement always has the same layout, whether you made one transaction or a hundred.

HTTP headers

  • Accept (request): the format the client wants back, like application/json.
  • Authorization (request): login credentials or a token.
  • Content-Type (both): the format of the body being sent.

Real-life example: the label on a parcel, saying what's inside and who's allowed to open it.

Status codes

  • 200 OK: success.
  • 201 Created: a new resource was added.
  • 400 Bad Request: invalid input.
  • 401 Unauthorized: you need to log in.
  • 403 Forbidden: logged in, but not allowed.
  • 404 Not Found: the resource doesn't exist.
  • 500 Internal Server Error: something broke on the server.

Real-life example: 2xx is "done", 4xx is "you need to fix something", 5xx is "our system is down, sorry".

Best practices

  • Name endpoints after resources, not actions: /api/books, not /getAllBooks.
  • Let the HTTP method say the action.
  • Use pagination so you never send thousands of rows at once.
  • Log activity and turn on SQL logging while developing.

Pagination

Add a Pageable parameter. The caller sends page, size and sort, for example /api/books/paged?page=0&size=5&sort=title,asc gives the first 5 books sorted by title. Page numbers start at 0.

Real-life example: the app shows 10 transactions at a time with a "Load more" button.

Testing with cURL

cURL sends requests from the terminal, so you can test the API without building a front end. -X sets the method, -H sets a header, and -d sends the data.

Pseudocode: GET one book


LOG "fetching book id"
book = repository.findById(id)
IF book exists
    RETURN 200 with ApiResponse(true, "Book found", book)
ELSE
    RETURN 404 with ApiResponse(false, "Book not found", null)

Pseudocode: POST a book


VALIDATE the JSON body (@Valid)
IF invalid -> 400 (handled by the global error handler)
saved = repository.save(book)
RETURN 201 with ApiResponse(true, "Book created", saved)

Tips for understanding the logic

  • Read an endpoint as METHOD + URL: "GET /api/books/3" means "read book 3".
  • Check the status code first, then the body.
  • ResponseEntity lets you choose the status code and the body together.
  • If cURL gets a 401, Spring Security is switched on. Log in or permit the endpoint while testing.
