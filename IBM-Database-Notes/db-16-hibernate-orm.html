Introduction to Hibernate and ORM

Acronyms

  • ORM: Object-Relational Mapping, using Java objects instead of writing SQL to work with tables.
  • JDBC: Java Database Connectivity, the manual way, where you write every query.
  • HQL: Hibernate Query Language, queries written against classes and fields, not tables and columns.
  • CRUD: Create, Read, Update, Delete.
  • CMS: Content Management System, like a blog or news site backend.
  • JPA: Jakarta Persistence API, the standard rulebook. Hibernate is the most popular library that follows it.

Why ORM

With JDBC you write complex queries, map every ResultSet row to an object by hand, repeat the same CRUD code, and manage relationships yourself. ORM bridges objects and tables so you save and load Java objects and the SQL is generated for you.

Real-life example: JDBC is translating every sentence yourself. ORM is a translator who sits between you and the client.

Hibernate

An open-source ORM framework for Java. It generates the SQL and manages relationships like one-to-many and many-to-many.

Advantages:

  • Database independence: change the dialect, not your code.
  • Less boilerplate: no repeated SQL for CRUD.
  • Caching: reuses data it has already loaded.
  • Lazy and eager loading: you control when related data is fetched.

Lazy vs eager loading

Lazy: related data loads only when you actually ask for it. Eager: related data loads straight away with the main object.

Real-life example: lazy is opening a client's file and only pulling their transaction history if you need it. Eager is pulling the whole history every time, just in case.

Architecture

  • Configuration: loads settings from hibernate.cfg.xml.
  • SessionFactory: built once. Holds the connection settings and hands out sessions. Expensive to create.
  • Session: short-lived, one per request or unit of work. Does the CRUD.
  • Transaction: groups operations so they all commit or all roll back.
  • Query / HQL / Criteria API: ways to fetch data. Hibernate turns them into database-specific SQL.
  • Entity classes: Java classes mapped to tables.

Real-life example: the SessionFactory is the bank's head office, set up once. A Session is one teller shift. A Transaction is one client's full set of actions that either all go through or none do.

Entity states

  • Transient: a new object Hibernate doesn't know about yet (new Book()).
  • Persistent: linked to an open session. Changes are synced to the database automatically on commit.
  • Detached: the session closed, so it still represents a row but changes aren't tracked any more.

Real-life example: a form you've filled in but not handed over (transient), a form the teller is busy capturing (persistent), and your copy you took home (detached).

Workflow

  1. Load configuration.
  2. Build the SessionFactory.
  3. Open a Session.
  4. Begin a Transaction.
  5. Work with entities (save, get, update, query).
  6. Commit (or roll back on error). Hibernate flushes changes to the database.
  7. Close the Session.

Mapping annotations

  • @Entity: this class is a table.
  • @Table(name = "books"): the exact table name.
  • @Id: the primary key.
  • @GeneratedValue(strategy = GenerationType.IDENTITY): the database generates the ID.
  • @Column(nullable = false, length = 100): column rules, like required and maximum length.

Real-world uses

  • E-commerce: large catalogues with products linked to categories and orders, lazy loading for speed.
  • Employee systems: hierarchies, payroll, inheritance mapping for different employee types, caching.
  • Finance: transactions that must be atomic, plus connection pooling and dialects.
  • CMS: articles and tags with HQL queries and eager fetching.

Pseudocode: saving and reading a book


AT STARTUP
    factory = build SessionFactory from hibernate.cfg.xml

SAVE
    open session
    begin transaction
    book = new Book (transient)
    session.persist(book) (now persistent)
    commit (Hibernate writes the INSERT)
    close session (book is now detached)

READ
    open session
    book = session.get(Book, id)
    close session

AT SHUTDOWN
    close factory

Tips for understanding the logic

  • One SessionFactory for the whole app, many short Sessions.
  • Always close the Session, ideally with try-with-resources.
  • If anything fails inside a transaction, roll back.
  • Spring Boot and Spring Data JPA do all of this for you. Seeing it by hand helps you understand what's underneath.
