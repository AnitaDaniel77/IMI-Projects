git-09: Overview of Git Workflows

What this lesson covers

The steps in a Git workflow, shown two ways: joining a team's existing project, and starting a new project from scratch. A clear workflow helps avoid code conflicts and overwriting a teammate's work.

Scenario in the video

I join a team building an e-commerce platform and my task is a product recommendation feature. The team uses Git and GitHub, so I need to know how to work with them without breaking anyone's code.

Workflow 1: joining an existing project

  1. Clone the team's repository from GitHub. This copies the code and its complete version history to my computer. The connection from cloning is what lets me push my changes to the remote repository and pull theirs into mine.
  2. Create a branch from main and work on it. A branch is an isolated development space based on main, so I can try different ways of coding the feature without touching the main code until it's ready.
  3. Develop the feature by changing the project files in my local repository.
  4. Move the changed files to the staging area, a temporary space where I collect the files I want Git to save.
  5. Commit the staged files to my branch with a clear message, such as "Implemented product recommendation feature". The message gives context to me and my teammates.
  6. Push the branch to the remote repository.
  7. Create a pull request, which asks the maintainer (the person responsible for managing the repository) to review and approve my changes.
  8. After the maintainer merges it, my changes are in main. If I have maintainer access, I review and approve other people's pull requests the same way.

Real-life example: a restaurant kitchen. I cook my new dish on a separate station (branch), put the ingredients out on the pass (staging), plate it with a label saying what it is (commit), and send it to the head chef (pull request). It only goes on the menu (main) once she approves it.

Workflow 2: starting a new project from scratch

  1. Initialize my local project folder as a Git repository, so Git starts tracking changes in it.
  2. Select all the files I want tracked and move them to the staging area.
  3. Make the initial commit.
  4. Create a blank remote repository and link my local repository to it.
  5. Push all the project files to the remote repository.
  6. Other developers clone it and follow the regular workflow.

Real-life example: setting up a new shared drive. I build the first folder on my own laptop, create the empty shared drive, connect them, upload everything, and then the rest of the team can copy it down and start working.

The use case: Anne and John

  • Anne, the lead developer, initializes a repository in her working directory, creates the project files, stages them, makes the initial commit, and pushes to a blank remote repository she created.
  • All developers clone it and start working on branches.
  • John builds user authentication. He creates a branch called User Auth from main, completes the feature, commits to that branch, tests it thoroughly, pushes the branch and creates a pull request.
  • Anne reviews and approves it, which merges John's changes into main so everyone can get them. Other developers do the same for their features.
  • When feature development is complete, Anne creates a release branch called Release 1.0 from main in the remote repository.
  • The team pulls the changes to bring their local repositories up to date, then does final testing, bug fixes and documentation updates on the Release 1.0 branch. They commit, push, and create a pull request.
  • Anne reviews and merges it into main and tags the release as Release 1.0.

Banking example: a new feature such as a fraud rule goes on its own branch, is reviewed by a senior developer, and merges into main. When enough features are done, a release branch is cut for final testing before the version goes live.

Pseudocode: both workflows

``` JOINING A PROJECT: clone the remote repository create a branch from main edit files stage the changed files commit with a clear message push the branch to the remote create a pull request maintainer reviews and merges into main STARTING A PROJECT: initialize a git repository in my folder stage the files I want tracked make the initial commit create a blank remote repository link local repository to remote push everything others clone and use the joining workflow RELEASING: create a release branch from main everyone pulls the latest changes test, fix bugs, update documentation on the release branch commit, push, create a pull request merge into main and tag the release ```

Tips for understanding the logic

  • Remember the order: clone, branch, edit, stage, commit, push, pull request. Say it out loud until it flows.
  • Staging is the step beginners skip over. It's the chance to choose exactly what goes into the next commit.
  • Push sends my commits to the remote. Pull brings other people's commits to me. Pull before I start work each day.
  • A tag, like Release 1.0, marks a specific point in history so the team can always find that version again.
  • Joining a project starts with clone. Starting a project starts with initialize.

Recap

When I join a project: clone, branch from main, stage, commit, push, pull request, review and merge. When I start one: initialize, stage, initial commit, create a blank remote, link, push, and let others clone it.
