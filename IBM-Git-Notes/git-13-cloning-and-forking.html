Git 13: Cloning and Forking GitHub Projects

IBM Git and GitHub course, Module 2. After this lesson you can clone and sync a repository, fork a project as the base for your own work, and use git commands to talk to other developers.

1. Clone versus fork

Cloning makes a copy of a repository on your own computer, and that copy stays linked to the original so you can keep the two in sync. Forking makes a copy of a repository on GitHub under your own account, so you can change or extend it without touching the original.

Analogy: cloning is photocopying a recipe book to keep in your kitchen, still stamped with the library's address so you can check for new editions. Forking is buying your own copy of the book to write your own version of the dishes in, without changing the author's book.

Tip: ask "where does the copy live?" A clone lives on your computer. A fork lives on GitHub.

2. How to clone

Open the repository on GitHub, click Code, and copy the HTTPS URL with the clipboard button. In a terminal, move to the folder where the copy should go, type git clone followed by the URL, and press Enter. Download ZIP also gives you the files, but without the version control history, so you cannot sync it later.

Analogy: a ZIP is a photo of the house. A clone is a key to the house, with the whole building history inside.

Tip: clone into a practice folder, never inside another git repository, or you end up with a repo inside a repo.

3. Sending your changes back: add, commit, push

After you edit files, git add moves the changed files into the staging area. The staging area is where a commit is shaped and reviewed before it is final. git commit -m with a message records what is in the staging area. git push then sends the committed changes to the repository on GitHub.

Analogy: packing a parcel. Add is putting items in the box, commit is sealing the box and writing the label, push is handing it to the courier.

4. Remote repositories

A remote is a repository stored somewhere else: on the internet, on your network, or even on your own computer. You can have several remotes, and each one is usually read-only or read-write for you. Working with others means moving work to and from them using push, fetch and pull.

Analogy: a shared drive. The remote is the shared drive, your clone is the copy you work on at home.

5. Push, fetch and pull

Push sends your commits to the remote. Fetch brings the remote's new changes into your local repository but does not merge them into the branch you are on, so you can look first and merge manually when you are ready. Pull does fetch and merge in one step, which is quicker but merges automatically, and that is not always what you want.

Analogy: fetch is checking the mailbox and reading the post on the table. Pull is checking the mailbox and putting everything straight into your filing cabinet.

Tip: when you are unsure what changed, fetch first and read, then merge.

6. Origin and upstream

These are just names for remotes. By convention, origin is your own copy (usually your fork) and upstream is the original project you forked from. You can name them anything, but sticking to the convention makes your repos easy for other developers to read.

Analogy: origin is your own shop, upstream is the head office that supplies the products.

7. Why fork

You fork to use a project as the base for something new, to work on a project independently, or to suggest improvements. When you are happy with your changes you open a pull request, and the original owner decides whether to accept them. Keep a copy of the license file when you fork. It is often a legal requirement, and good practice even when it is not.

Tip: a pull request is a polite question: "would you like these changes?"

8. Keeping your fork in sync

The original project keeps moving after you fork it, so your fork needs to catch up. Clone your fork, check the remotes with git remote -v, then add the original repository as a remote called upstream. Run git fetch upstream to download its branches, then git merge upstream/main to bring its changes into your main branch. git pull upstream does the fetch and merge together.

Real example: your PayNest capstone is a fork of Hilbert's repo. Your fork is origin, and his repo is upstream. That is exactly this setup.

9. Pseudocode

Clone, change and push:

```text go to the repository page on GitHub copy the HTTPS clone URL in the terminal, move to the practice folder run git clone with the URL -> full copy with history edit the files git add the changed files -> staging area git commit with a message -> saved in local history git push -> GitHub receives the commits ```

Keeping a fork in sync:

```text clone your fork -> remote origin points to your fork list remotes and check origin add the original repo as upstream fetch upstream -> download new work, change nothing yet look at what came in merge upstream/main into main -> your branch catches up push to origin -> your fork on GitHub is current too ```

10. Summary

GitHub has over 100 million repositories you can learn from or build on. Clone to copy a repository to your machine and sync changes. Fork to use a repository as the base of a new project or to work on it independently, and send changes back with a pull request.
