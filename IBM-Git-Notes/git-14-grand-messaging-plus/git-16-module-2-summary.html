Git 16: Module 2 Summary, Git Workflows with Git Commands

IBM Git and GitHub course, Module 2 recap. This page pulls together the workflow, the roles and the commands from the whole module.

1. Clone and fork in one line each

GitHub has over 100 million repositories. You can clone a repository and sync changes back to the original. You can also fork a repository to use it as the base of a new project or to work on it independently.

2. The GitHub workflow, step by step

  1. Clone the remote repository, or initialise a new Git repository.
  2. Move files to the staging area.
  3. Make the initial commit.
  4. Create a branch and work on it.
  5. Add files to the staging area and commit again.
  6. Push the local commits to the remote repository.
  7. Create a pull request for review and merging.
  8. Use pull to update your local repository.

Analogy: writing a group report. You get a copy of the shared document, draft your section, save versions as you go, send your section in, wait for the team to review, then download the final merged version.

Tip: the workflow is a loop. After step 8 you start again at step 4 for the next piece of work.

3. The three roles

The developer uses git clone, git pull, git fetch, git push and git request-pull, on top of the commands a solo developer uses. The integrator reviews and integrates other people's changes using git pull, git revert and git push, on top of the developer commands. The repository administrator structures the repository, controls how users interact with it, configures servers for web services and documentation, defines email and index settings, and manages the look and feel of the application.

5. The less familiar commands

git format-patch turns commits into patch files you can send to someone, git send-email sends them by email, and git am applies a received patch to your repository. Analogy: instead of sharing the whole document, you email just the tracked changes.

git daemon serves your repositories over the git protocol so others can clone them from your machine. git instaweb (and git web) opens a quick web view of your repository in the browser.

git rerere stands for "reuse recorded resolution". Git remembers how you solved a merge conflict once and applies the same fix if the same conflict appears again.

git reset moves your branch back and can discard work, especially with --hard, so use it carefully. git revert is the safe undo for shared branches because it adds a new commit that cancels the old one.

The table also lists git-pull downstream. The lesson does not explain it, but the idea is pulling work from a repository that was forked from yours (a downstream repo). Treat it as vocabulary rather than a command to memorise.

6. Pseudocode

```text get the code: clone the remote repo (or git init for a new project) save the first version: add files to staging commit for each new piece of work: create a branch and switch to it edit files add and commit push the branch to the remote open a pull request reviewer fetches, diffs and merges pull main to update your local copy keep a fork current: add upstream as a remote fetch upstream merge upstream/main into main ```

7. Tips for remembering

Group commands by the question they answer. "Where am I?" is status, log and diff. "How do I save?" is add and commit. "How do I share?" is push, pull and fetch. "How do I undo?" is revert and reset. The remote commands are the glue between your computer and GitHub.
