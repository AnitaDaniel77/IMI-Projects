Module 1: Object-Oriented Programming Basics

Objects and Classes

An object is a specific instance with its own values, like one particular red sports car that can be driven and honked. A class is the blueprint those objects come from, it defines what properties and methods every car has, without being any one car itself.

Real-life example: the class is the car factory's design spec. Every car built from it is an object with the same kind of features, but its own color, speed and mileage.

Logic: define the shape once (the class), then stamp out as many objects from it as needed, each filling that shape with its own values.

class Car:
    color
    speed

    function drive():
        print color + " car is driving"

myCar = new Car()
myCar.color = "red"
myCar.speed = 180
myCar.drive()  // prints: red car is driving

Properties and Methods

Properties are what an object has (color, speed, model). Methods are what an object does (drive, honk, park). Every object made from the same class shares the same set of properties and methods, but fills them in with its own values.

Inheritance

Inheritance lets a new class reuse an existing class's properties and methods, then add or specialise its own, like a family tree where a child inherits traits from a parent but can also have its own.

Real-life example: an electric car and a sports car are both still cars, so they inherit color, speed and drive() from Car, but the electric car adds batteryLife and the sports car adds a boost() method.

Logic: the subclass gets everything the parent class has for free, and only needs to define what's different about it.

class ElectricCar extends Car:
    batteryLife  // extra property only electric cars have

class SportsCar extends Car:
    function boost():  // extra method only sports cars have
        print "Accelerating fast!"

Encapsulation

Encapsulation bundles an object's data with the methods that operate on it, and hides the internal details behind that bundle so the outside world only sees what it needs to.

Real-life example: a TV remote. You press power, channel or volume, you don't need to know how the signal processing or screen rendering works inside. The remote is the exposed interface, the wiring is hidden.

Logic: keep the sensitive or complicated internal detail private, and expose only the small set of actions the outside world is allowed to use.

Polymorphism

Polymorphism means different objects can respond to the same method call in their own way. One method name, many behaviours, depending on which object is actually running it.

Real-life example: a helicopter and a rocket both have a fly() method. Call fly() on the helicopter and it spins its rotor blades; call fly() on the rocket and it fires its engines. Same method name, completely different behaviour underneath.

Logic: code that calls fly() doesn't need to know or care which kind of object it's calling it on, it just trusts each object to know how to fly itself.

Applied example: online bookstore

Book is a class with properties like title, author, price, and methods like displayInfo() and applyDiscount(). Customer is a separate class with its own properties (name, email, address) and methods (createAccount(), placeOrder()).

  • Inheritance: an Ebook class extends Book and adds a fileFormat property.
  • Encapsulation: a customer's password is kept as a private property, only accessible through controlled methods, not exposed directly.
  • Polymorphism: a shared PaymentMethod interface is implemented by both CreditPayment and PayPalPayment, so a customer can pay either way through the same interface.

How to think about it

When a lesson introduces a new OOP concept, the quickest way to check you've actually understood it, not just memorised the definition, is to ask: what real object plays this role, and what would break if this concept weren't here? If encapsulation didn't exist, every class using Book would have to know exactly how price and discount math work internally. If polymorphism didn't exist, you'd need a separate, differently-named method for every payment type instead of one shared payment interface.
