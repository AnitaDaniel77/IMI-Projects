Module 2: Polymorphism

What polymorphism is

Polymorphism lets objects share the same interface (same method name/call) while each behaves differently based on its own implementation. It's what gives object-oriented code its flexibility, you can write code that works with a general type and trust each specific object to handle it correctly on its own.

Real-life example: a fingerprint. It's one single key, but depending on where you use it, it unlocks your phone, marks attendance, or authorises a payment, same interface (the fingerprint scan), different outcome depending on context.

There are two types: compile-time polymorphism (method overloading) and runtime polymorphism (method overriding).

Compile-time polymorphism (method overloading)

Multiple methods in the same class share the same name but differ in their parameters, either how many, or what type. Java figures out which one to run at compile time, based on what you pass in.

Real-life example: ordering "a coffee", "a coffee with milk", or "a coffee with milk and sugar" are all valid orders using the same word "coffee", the specifics you give decide which version you actually get.

Logic: the method name stays the same, the signature (parameter types/count) is what makes each version distinct, Java matches your call to the version whose parameter list fits.

class MathOperations:
    function add(a, b):              // two ints
        return a + b

    function add(a, b, c):           // three ints
        return a + b + c

    function add(a: double, b: double):  // two doubles
        return a + b

// which version runs is decided by what you pass in, at compile time
math.add(2, 3)
math.add(2, 3, 4)
math.add(2.5, 3.5)

Runtime polymorphism (method overriding)

A subclass provides its own version of a method already defined in its superclass. Which version actually runs is decided at runtime, based on the object's real type, not the type of the variable holding it.

Real-life example: declare a variable as Animal, but assign a Dog to it, calling sound() still runs Dog's "Dog barks" version, not Animal's generic one, because the actual object underneath is a Dog.

Logic: the reference type controls what you're allowed to call, the object's actual type controls which version of that call executes.

class Animal:
    function sound():
        print "Animal makes a sound"

class Dog extends Animal:
    function sound():
        print "Dog barks"

class Cat extends Animal:
    function sound():
        print "Cat meows"

myAnimal = new Dog()
myAnimal.sound()   // prints "Dog barks", decided at runtime by actual object type

myAnimal = new Cat()
myAnimal.sound()   // now prints "Cat meows"

Virtual methods

In Java, every non-static method is "virtual" by default, meaning it can be overridden and Java will always run the subclass's version at runtime if one exists, regardless of the reference type used to call it. There's no special keyword needed to opt into this, it's just how Java behaves.

Why polymorphism matters

  • Code reusability: write generic code (like a method that takes an Animal) without needing to know the exact subtype in advance.
  • Decoupling: the code that uses an interface doesn't need to know how it's implemented, so the two can change somewhat independently.
  • Dynamic behaviour: useful in complex systems where the right behaviour genuinely depends on the object at runtime, not something you can hardcode upfront.
  • Frameworks: lets a framework define structure while letting users plug in their own implementations.
  • Maintenance: changes to one subclass's behaviour don't ripple out and force changes everywhere else that uses the general type.
