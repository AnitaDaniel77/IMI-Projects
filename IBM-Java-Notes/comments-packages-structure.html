Java Code Structure and Comments

Comments — three types

  • Single-line (`//`) — everything after it on that line is a comment.
  • Multi-line (`/* ... */`) — can span several lines, can also follow code on the same line.
  • Documentation comments (`/** ... */`) — a special multi-line format read by tools like Javadoc to auto-generate documentation, using `@param` and `@return` tags to describe a method's inputs and output.

Why comments matter

  • Clarity — explains complex logic for others (and future you).
  • Maintenance — provides context when revisiting code later, reducing confusion.
  • Collaboration — helps team members understand each other's work.

Packages

Group related classes and interfaces together, avoiding naming conflicts and keeping large projects manageable. Declared with `package com.example.myapp;` at the very top of the file. The folder structure on disk must physically mirror the package name — `com.example.myapp` becomes nested folders `com/example/myapp/`.

File and naming conventions

  • Each public class lives in its own file, named exactly after the class (`Book` class → `Book.java`).
  • camelCase for variables and methods — first word lowercase, each following word capitalized.
  • Every Java application needs an entry point — a `main` method inside a public class.
  • Classes from other packages must be `import`ed at the top of the file (e.g. `import java.util.ArrayList;`).

Real banking example

This package structure is exactly why your PayNest capstone code lives under `com.paynestsystem.payment` — Capitec-scale projects have hundreds of classes, and packages are what keep a `Payment` class in the payments module from colliding with an unrelated `Payment` class someone else might create in a different module.

Best practices for beginners

  • Meaningful names — `Customer` over `C1`; makes intent obvious to any reader.
  • Logical organization — group related classes into packages matching real project modules (e.g. separate folders for authentication vs product management).
  • Comment wisely, not obviously — explain *why* a decision was made, not what the code already visibly does (`i++` doesn't need "// incrementing i by 1").
  • Consistent formatting — indentation, spacing, brace placement, ideally enforced automatically by your editor.
  • Understand execution flow — Java runs top-to-bottom within a method, starting from `main` as the entry point.

Worked example

The lesson builds a small library system: a `Book` class (with `title`, `author` fields and a constructor) inside `com.example.library`, and a `Library` class that stores books in an `ArrayList`, adds them, and displays them — with `main` as the entry point that creates the library, adds a couple of books, and prints them out.

Logic to hold onto

Packages and file-naming rules aren't arbitrary bureaucracy — they're what lets thousands of files across a huge codebase stay organized and conflict-free. A comment's job is to answer a question the code itself can't answer just by being read — if the code already makes something obvious, the comment is noise; if the code hides a non-obvious reason behind a decision, that's exactly what the comment should capture.
