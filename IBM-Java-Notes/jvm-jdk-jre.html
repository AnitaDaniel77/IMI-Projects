Java Virtual Machine, Development Kit, and Runtime Environment

JVM (Java Virtual Machine)

The abstract machine that makes Java platform-independent. When Java code compiles, it becomes bytecode. The JVM converts that bytecode into machine code the operating system understands — a process called JIT (just-in-time) compilation. The JVM also handles memory management through garbage collection, automatically freeing memory no longer in use, which helps prevent memory leaks.

Analogy

Writing a letter in English to someone who only speaks Spanish — they need a translator. The JVM is that translator, converting bytecode into machine code the OS can actually run.

JDK (Java Development Kit)

The full software package needed to build, compile, and run Java applications. Contains:

  • The JRE (needed to execute programs)
  • Development tools — the javac compiler, debuggers, other utilities
  • Java APIs — reusable libraries for common tasks

Workflow: write a `.java` file → compile it into bytecode using javac (part of the JDK) → run that bytecode via the JVM, which lets it run on any platform.

Analogy

A carpenter's full toolbox — the complete set of tools needed to build anything, from a simple program to a complex system.

JRE (Java Runtime Environment)

Provides the environment needed to actually execute Java applications — includes the JVM, core libraries, and other runtime components. Does not include development tools like compilers. Manages loading class files and executing them via the JVM. With just the JRE installed, you can run Java programs without needing the full JDK.

Analogy

A fully furnished room, ready to live in — everything needed to function is there (JVM, libraries), but if you need to build or renovate, those tools live in the JDK, not here.

How the three relate

  • JVM — the engine that executes bytecode; included inside both the JDK and JRE.
  • JRE — provides what's needed to run applications (including the JVM), but no development tools.
  • JDK — the complete kit: JRE + development tools, used for actually building applications.

Use the JDK when developing (coding, compiling, debugging). Use just the JRE when you only need to run existing Java applications without building or modifying them — it's lighter since it skips the development tooling.

Real banking example

This distinction matters practically: a developer's machine at Capitec needs the full JDK to write and compile Java code, but a production server running the finished application might only need the JRE installed — no reason to ship development tools onto a server that's just executing already-compiled code.

Version alignment

The JDK, JRE, and JVM are versioned and updated together — as of this lesson, the latest stable JDK is Java 23 (released September 2024), with the JRE and JVM aligned to match. JVM updates specifically also come through Oracle's quarterly and critical patch updates. Java evolves continuously, so version numbers will keep moving forward.

Logic to hold onto

Think of it as three nested layers, from broadest to narrowest: JDK (the whole toolkit) contains the JRE (the running environment) which contains the JVM (the actual execution engine). If you're only ever running finished Java programs, you technically only need the innermost two layers (JRE, which bundles the JVM). The moment you want to write or compile your own code, you need the full outer layer — the JDK.
