Approaches to Application Architecture

What a component is

An individual unit of encapsulated functionality that works alongside other components to form part of an application. Six defining characteristics:

  • Reusable — designed to be used across different applications, not just one.
  • Replaceable — can be swapped for another component without disruption.
  • Independent — doesn't depend on other components.
  • Extensible — new behavior can be added without changing other components.
  • Encapsulated — data and methods are bundled together, hiding internal state and implementation.
  • Non-context-specific — works across different environments; the data that sets its internal state is passed in, rather than baked into or reached for by the component itself.

Examples of components

  • A reusable API connecting a system to a specific database.
  • A data access object — an interface for a database that can switch which database it talks to without the application even knowing the switch happened.
  • A controller — decides which other components need to be called for a given event, controlling data flow between them.

Component-based architecture

Focuses on decomposing a system's design into these logical components. Provides a higher level of abstraction than plain object-oriented design — it defines, composes, and implements loosely coupled, independent components that work together to form the whole application.

Real banking example

Your PayNest `PaymentMethod` interface with `CardPayment`/`EftPayment`/`WalletPayment` hits several of these characteristics directly: replaceable (swap in a new payment type without touching `PaymentProcessor`), independent (each implementation doesn't depend on the others), and encapsulated (each payment type's internal logic is hidden behind the shared interface).

Services vs components

A service is also a unit of functionality, but designed to be deployed independently and reused by multiple systems, focused on solving a specific business need. The key distinction: a service has exactly one unique, always-running instance that multiple clients communicate with — a component doesn't necessarily have that "single running instance" property.

Layering, from smallest to largest: objects make up components, and components make up services. A service is technically a type of component, just one meant to be deployed independently of the overall system.

Examples of services: checking a customer's credit, calculating a monthly loan payment, processing a mortgage application.

Real banking example

"Calculating a monthly loan payment" as a named example service is directly relevant to Capitec — that's likely a genuinely independent, always-running service in their real architecture, callable by the mobile app, the website, and internal staff tools alike, all hitting the same single running instance rather than each having their own separate calculation logic.

Service-Oriented Architecture (SOA)

Services are loosely coupled and communicate with each other via a communication protocol over a network. SOA supports building distributed systems that deliver services to other applications through that protocol.

Distributed systems

Multiple services running on different machines, coordinating by passing messages over a protocol like HTTP. Despite running across multiple machines, a distributed system appears to the end user as one single, coherent system.

Key properties

  • Shares resources — hardware, software, data.
  • Fault-tolerant — if one node or service fails, the system keeps running; the system can change during execution without interrupting service.
  • Concurrent — multiple activities run at once, reducing latency and increasing throughput.
  • Scalable — handles growth in users without a fundamental redesign.
  • Heterogeneous — the machines involved don't need matching hardware, operating systems, or even programming languages.

A node is any device on the network that can recognize, process, and transmit data to other nodes. A distributed system is made of multiple interconnected nodes, each running one or more services in an SOA setup.

Common base architectures for distributed systems: client-server, three-tier, peer-to-peer, microservices (each covered in more depth later).

Real banking example

Capitec's core banking infrastructure is almost certainly a distributed system by this definition — the app, ATMs, in-branch systems, and card payment processing all need to work together and appear seamless to you as a customer, even though they're realistically running as separate services across many machines. Fault tolerance matters enormously here: if one service (say, an ATM's connection) has an issue, the rest of the banking system shouldn't go down with it.

Logic to hold onto

The nesting relationship is the key thing to remember: objects → components → services → distributed systems, each level built from the one below it. A component becomes a service specifically when it's built to run as one independent, always-available instance shared across multiple clients — that single distinguishing property is what separates "a reusable piece of code" from "a service other systems can rely on."
