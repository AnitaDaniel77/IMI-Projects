Application Deployment Environments

What an application environment is

The combination of hardware and software needed to run an application: the code/binaries, the software stack it depends on (libraries, third-party apps, middleware), the operating system, networking infrastructure, and the physical or virtual hardware (compute, memory, storage).

Pre-production environments

The stages an application passes through before going live:

  • Development — where the application is actively being coded; often just the developer's own workstation.
  • QA (testing) — where the QA team tests the application's components.
  • Staging — as close a replica of production as possible, but not exposed to general users.

Production

The full solution stack — hardware, software, and infrastructure — that the live application runs on, intended for all real users. Unlike pre-production environments, production has to account for actual application load — potentially thousands or millions of simultaneous users for enterprise-level apps — plus non-functional requirements like security, reliability, and scalability. This makes production genuinely more complex than any pre-production stage.

Real banking example

This maps directly onto how your own capstone work should be thought about at scale: your `complete-website-AnitaDaniel` repo running locally in VS Code is your development environment. At Capitec, before a Java feature reaches customers, it would move through development → QA → staging, with staging specifically designed to catch anything that only shows up under production-like conditions (real data volume, real network setup) before millions of Capitec customers ever touch it.

Deployment options

On-premises

The system and infrastructure live in-house, within the organization's own physical location, typically behind a firewall (which blocks unauthorized network access). The organization is fully responsible for the hardware, infrastructure, and maintenance. Chosen when greater security or control over the application and its data is needed — but it's generally more expensive than cloud deployment.

Cloud — three models

  • Public cloud — infrastructure owned by a cloud provider, shared across multiple companies, accessed over the open internet. Providers: AWS, Microsoft Azure, Google Cloud, IBM Cloud. Most common option, due to scalability and cost.
  • Private cloud — provisioned for exclusive use by a single organization; can run on-premises or be owned/managed by a service provider (even AWS offers private cloud services). Main advantage: increased security, plus flexibility since it can be fully customized.
  • Hybrid cloud — a combination of public and private clouds working together, aiming to capture the advantages of both — cost, security, scalability, and flexibility — depending on which workload sits where.

Real banking example

A bank like Capitec is a strong candidate for a hybrid cloud approach — highly sensitive data (account records, transaction history) might sit in a private cloud or on-premises for maximum security and regulatory control, while less sensitive, high-traffic components (like the public marketing website or app store distribution) could run on public cloud infrastructure for cost and scalability benefits. This is exactly the kind of trade-off "on-premises vs public vs private vs hybrid" decisions come down to in a regulated financial environment.

Logic to hold onto

The pre-production stages exist to progressively de-risk a release: development catches basic mistakes, QA catches functional bugs, staging catches anything that only appears under near-production conditions. Production is where all of that risk-reduction work either pays off or gets tested against reality at scale. The deployment model choice (on-prem, public, private, hybrid) is a separate but related decision — it's about where that whole pipeline physically runs, driven by a trade-off between cost, control, security, and scalability specific to what the organization actually needs.
