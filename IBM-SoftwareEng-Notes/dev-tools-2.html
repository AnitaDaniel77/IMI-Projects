More Application Development Tools

CI/CD

Continuous Integration and Continuous Delivery/Deployment — a DevOps best practice for shipping frequent, reliable changes.

  • CI — run through a build-automation server, ensures all code components work together smoothly by integrating newly written code frequently (daily, sometimes hourly, depending on how fast the project moves).
  • CD — picks up where CI ends. Once CI has automatically built and tested the code, CD deploys those changes to a testing or staging environment.

Real banking example

At a bank, frequent small integrations catch problems early — if ten developers are all touching the same payments codebase, CI running daily (or hourly) means a broken change gets flagged within hours, not discovered weeks later when it's tangled up with dozens of other changes.

Build tools

Transform source code into the binaries needed for installation — organizing code, setting compile flags, and managing dependencies. Most critical in environments with many interconnected projects and multiple contributors, where manually tracking changes, order, and dependencies becomes unmanageable without automation.

Build automation can handle: downloading dependencies, compiling source into binary, packaging that binary, running tests, and deploying to production. Can be triggered from the command line or an IDE.

Two categories:

  • Build-automation utilities — generate build artifacts (executables) by compiling and linking source code.
  • Build-automation servers — run those utilities on a scheduled or triggered basis.

Examples: Webpack (JavaScript module bundler), Babel (JavaScript compiler), WebAssembly (binary instruction format that runs in the browser).

Real banking example

This is exactly what Maven does for your PayNest capstones — it compiles your Java source, manages dependencies, and runs your test suite (like the 8/8 passing tests on Capstone 1) automatically, rather than you manually compiling and testing every file by hand each time.

Packages

Archive files bundling app files, installation instructions, and metadata together, so the end user has a simple, trouble-free install. Packages carry their own metadata: description, version, and dependencies (other packages that must be installed first).

Package managers

Handle finding, installing, maintaining, and uninstalling software packages on request. Package management systems specifically:

  • Coordinate with file archivers to extract package archives
  • Verify checksums and digital certificates to confirm integrity and authenticity
  • Locate, download, install, or update software from a repository
  • Manage dependencies, ensuring a package installs alongside everything it requires

OS-level package managers

  • Linux — DPKG (Debian), RPM (Red Hat)
  • Windows — Chocolatey
  • Android — Package Manager
  • macOS — Homebrew, MacPorts

Language-level package managers

  • Node.js/JavaScript — npm
  • Java — Gradle and Maven
  • Ruby — RubyGems
  • Python — Pip and Conda

Real banking example

Maven, listed here as a Java package manager, is the same tool referenced in your dev environment notes — it's both a build tool AND a package manager for Java, handling dependency resolution (the reason the Zscaler corporate proxy issue affects your capstone repo specifically) alongside compiling and testing your code.

Logic to hold onto

These four tools form a pipeline, not four separate unrelated things: build tools turn your source code into something runnable, packages wrap that runnable thing up for distribution, package managers handle getting that package onto someone's machine correctly (with dependencies satisfied), and CI/CD automates the whole chain so it happens reliably and frequently instead of manually and rarely.
