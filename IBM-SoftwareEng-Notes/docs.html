Software Documentation

What documentation is

Information describing what a product is and how to use it — written, video, or graphical. It spans every phase of the SDLC and gets written for different audiences: end users, developers, QA engineers, system administrators, and other stakeholders.

Two categories: product vs process

  • Product documentation — relates to the product's functionality (what it does, how it's built).
  • Process documentation — describes how to complete a task, and should provide requirements for correctly executing a business process.

Five types of product documentation

1. Requirements documentation

Written during the Planning phase, for the development team (developers, architects, QA). Describes expected features and functionality. Includes the SRS, SysRS, and user acceptance specifications covered earlier.

2. Design documentation

Written by architects and the development team, explaining how the software will actually be built to satisfy the requirements. Includes both conceptual and technical design documents.

3. Technical documentation

Code comments that help other developers understand behavior, plus working papers explaining how the code works and documents capturing engineers' thinking during implementation.

4. Quality assurance documentation

Everything related to the testing team's strategy, progress, and metrics: test plans, test data, test scenarios, test cases, test strategies, and traceability matrices — documents that map test cases back to the specific requirements they're verifying.

5. User documentation

For end-users — explains how to operate, install, or troubleshoot the software. Includes FAQs, installation/help guides, tutorials, and user manuals.

Standard Operating Procedures (SOPs)

SOPs accompany process documentation but go into far more detail. Where process documentation gives an overview, an SOP is step-by-step, organization-specific instructions for a common but complex task. The example given: checking in code via a repository is general knowledge, but the *specific* steps an organization requires to actually get code merged into main — that level of detail is what an SOP captures. SOPs can be a flowchart, a hierarchical outline, or plain step-by-step instructions.

Keeping documentation current

Documentation has to be actively maintained — if a UI changes, the accompanying user manual has to be updated too, and businesses need to allocate real time/resources for this. Within the SDLC, documentation updates happen during the Maintenance phase, and ideally get periodically reviewed for accuracy even outside of active changes.

Logic to hold onto

Product vs. process is the first split (what it does vs. how to do a task), and the five documentation types are all sub-categories of *product* documentation specifically — process documentation and SOPs sit in their own separate lane. Stale documentation is arguably worse than no documentation at all, since it actively misleads instead of just being absent — which is exactly why Maintenance includes documentation upkeep as a real, ongoing responsibility, not a one-time task.
