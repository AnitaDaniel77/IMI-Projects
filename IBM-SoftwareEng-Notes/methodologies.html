Software Development Methodologies

Why methodology matters

A methodology is the specific approach a team follows to move through the SDLC — it shapes how the team communicates, when information gets shared, and how rigid or flexible the process is. Three common ones: Waterfall, V-shape, and Agile.

Waterfall

The original SDLC approach. Purely sequential — output of one phase becomes input for the next, and work on the next phase only starts once the previous one is fully complete. All planning (requirements, architecture) happens upfront. The customer typically doesn't see the product until it hits the testing phase. Major releases repeat this whole process, which means long gaps — sometimes years — between releases.

Pros: easy to understand, discrete well-defined stages so everyone knows their role, easier to estimate budget/resources since planning is all upfront.

Cons: inflexible — if a requirement changes or was missed, it's hard to work back in later. Since planning happens once at the start, unforeseen complications or shifting needs are painful to accommodate.

V-shape model

Named for its shape: the left side going down is "verification," the right side going up is "validation," meeting at the bottom in coding. Each verification phase pairs with a matching validation phase:

  • Planning ↔ Acceptance testing
  • System design ↔ System testing
  • Architecture design ↔ Integration testing
  • Module design ↔ Unit testing
  • Coding sits at the very bottom, the pivot point

Tests are actually written during the verification (left) phases, then executed during the matching validation (right) phases — so test plans exist before coding even starts.

Pros: simple, writing test plans early saves real time during coding and validation.

Cons: even more rigid than Waterfall — once in testing, going back to change functionality is extremely difficult. Same core weakness as Waterfall: poor accommodation of changing requirements.

Agile

A genuinely different approach — collaborative and iterative instead of linear. Work happens in short cycles called sprints (typically 1-4 weeks). Unit testing happens within every sprint to catch problems early and often. Instead of a single "maintenance" phase at the very end like traditional SDLC, each sprint ends with a feedback stage. At the end of a sprint, working code gets shown to stakeholders at a "sprint demo," feedback gets collected, and the whole cycle repeats for the next sprint.

After several sprints, teams often reach a Minimum Viable Product (MVP) — a basic but functional feature set stakeholders can react to, used to validate assumptions about the software before investing further.

The Agile Manifesto — four core values

  • Individuals and interactions over processes and tools
  • Working software over comprehensive documentation
  • Customer collaboration over contract negotiation
  • Responding to change over following a plan

Pros: handles new or changing requirements quickly and easily since planning happens fresh at the start of every sprint, not once at the beginning of the whole project. Modular design (breaking work into smaller integratable chunks) supports this well.

Cons: upfront budgeting and scheduling is genuinely harder, since the overall scope isn't locked down early the way it is in Waterfall.

Real banking example

A brand-new core banking system overhaul at Capitec — something huge, regulatory-heavy, with fixed compliance requirements known well in advance — might actually suit Waterfall or V-shape reasonably well, since the requirements are stable and testing needs to be rigorously pre-planned for audit purposes. But a customer-facing feature like tweaking the app's budgeting tool based on ongoing user feedback fits Agile far better, since customer needs and UI preferences shift and get refined sprint over sprint.

Logic to hold onto

The core dividing line is sequential vs. cyclical. Waterfall and V-shape assume you can nail requirements once, upfront, and build in a straight line from there — that assumption breaks down the moment requirements change. Agile assumes requirements *will* shift, so it rebuilds planning into every sprint instead of doing it once. Waterfall/V-shape trade flexibility for predictability; Agile trades predictability for flexibility. Neither is objectively "better" — the right fit depends on how stable the requirements actually are.
