Roles in Software Engineering Projects

Overview

Not every project has every role, and naming varies by company and methodology (Agile vs Waterfall especially). The common roles: project manager/Scrum master, stakeholder, system/software architect, UX designer, developer, tester/QA engineer, site reliability/Ops engineer, product manager/owner, and technical writer.

Project Manager vs Scrum Master

Traditional SDLC methods use a project manager — focused on planning, scheduling, budgeting, allocating personnel/resources, executing the plan, and team communication. Agile's equivalent is a Scrum master — but the focus shifts: instead of driving planning, they focus on team and individual success, facilitating the communication that Agile's core values prioritize over rigid process.

Stakeholder

The people the product is being built for — customers, end-users, decision-makers, system administrators, other key personnel. Mainly responsible for defining requirements and giving clarification/feedback when the team hits ambiguity or a proposed solution doesn't work as planned. Sometimes also participate directly in beta testing and acceptance testing.

System / Software Architect

Designs and describes the project's architecture, and communicates it to the team. Responsible for the inner structure and technical characteristics of the software, providing technical support across every SDLC stage (covered in more depth in a later module).

UX Designer

Balances making software intuitive with making it robust enough to actually meet requirements. Defines how the software behaves and communicates from the user's perspective — essentially owns how a human actually experiences interacting with the product.

Developer

Writes the code that powers the software. Responsible for implementing the architecture from the design document, incorporating the requirements from the SRS, and applying the UX requirements the UX designer defined. This is the role sitting at the intersection of the architect's structure, the requirements' spec, and the designer's user experience — turning all three into working code.

Tester / QA Engineer

Owns product quality and confirms the software actually meets customer requirements. Writes and runs test cases to catch bugs or deficiencies, then reports that feedback back to the development team.

Site Reliability Engineer (SRE) / Ops Engineer

Bridges development and operations, combining software engineering skill with IT systems management. Tracks incidents, runs incident-review meetings, automates systems/procedures, helps with troubleshooting, and generally keeps things reliable for the customer.

Real banking example

An SRE role is especially critical in banking — if a payment system goes down at Capitec, the SRE is the one tracking the incident, coordinating the response, and automating safeguards so it doesn't happen again. Uptime and reliability aren't optional in financial services the way they might be for, say, a games app.

Product Manager / Product Owner

Holds the overall vision for what the product should be. Deeply understands both client requirements and end-user needs. Leads the development effort and is responsible for making sure the finished product actually delivers the value stakeholders expect — the person ultimately answerable for "does this solve the right problem."

Technical Writer / Information Developer

Writes documentation for the end-user — translating technical material for a non-technical audience. Beyond helping end-users actually use the software, this documentation also helps the customer give the development team timely, informed feedback. Can include user manuals, reports, white papers, and press releases.

Logic to hold onto

Notice how neatly this maps back to the documentation types from the last lesson: requirements docs come from the stakeholder/product manager relationship, design docs come from the architect, technical docs come from developers, QA docs come from testers, and user docs come from the technical writer. Every documentation category traces back to a specific role that owns producing it — the roles and the artifacts aren't separate topics, they're two views of the same process.
