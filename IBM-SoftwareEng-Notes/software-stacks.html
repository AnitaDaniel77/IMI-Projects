Introduction to Software Stacks

What a software stack is

A combination of technologies — software and programming languages — stacked in a hierarchy that work together to run an application. Higher levels in the stack handle tasks/services for the user; lower levels interact directly with the computer hardware. A stack typically includes front-end tech (languages, frameworks, UI tools) and back-end tech (languages, frameworks, web servers, app servers, OS, messaging, databases).

Software stack vs technology stack

These terms often get used interchangeably, but a technology stack is broader — it includes hardware and infrastructure too (virtual machines, containers, storage, load balancers) on top of the software stack itself.

Basic structure

The simplest stack has three layers: presentation (what the user sees), business logic (the actual processing/rules), and data (storage). More complex applications add layers for virtualization, scheduling/orchestration, runtime environments, database connectivity, networking, and security. There's no formal required structure — the only rule is that everything included must support the application's development, functionality, or deployment. You only use the layers relevant to your specific solution.

Named stack examples

  • Python Django — Python + Django framework, open source, common for large-scale, fast-changing web apps.
  • Ruby on Rails — Ruby + a server-side framework, strong with JSON/XML for data transfer, HTML/CSS/JS on the front end.
  • ASP.NET — Microsoft-centric: ASP.NET MVC framework, IIS web server, SQL Server, Azure.

LAMP

Linux, Apache (web server), MySQL (database), PHP (language). One of the earliest software stacks, built for websites and cloud apps. Fully open source and loosely coupled — pieces are swappable. Example: replace MySQL with PostgreSQL and it becomes the LAPP stack; swap PHP for Python and it changes again.

MEAN, MEVN, MERN family

  • MEAN — MongoDB, Express.js, Angular, Node.js. Platform-agnostic, free, open source.
  • MERN — same as MEAN but React replaces Angular; flexible, high-performing front-end.
  • MEVN — same as MEAN but Vue.js replaces Angular; lighter-weight than Angular, sometimes better raw performance, but fewer available libraries since Vue is newer.

Trade-offs: MEAN vs MEVN vs LAMP

MEAN

Pros: everything runs on JavaScript, so developers only need one language across the whole stack. Open source, well-documented, huge library of free reusable Node.js modules speeds up development.

Cons: not ideal for very large-scale applications. With Express.js, business logic tends to live server-side, limiting reuse of some services (like batching operations). MongoDB handles unstructured data well but lacks the structured querying power of a relational database.

MEVN

Very similar tradeoffs to MEAN, but since Vue.js is newer than Angular, there's a smaller pool of existing reusable libraries to draw from.

LAMP

Pros: open source with a large amount of reusable code available; being one of the oldest stacks, support and existing solutions are easy to find.

Cons: tied to Linux specifically, making it less flexible than the platform-agnostic MEAN/MEVN stacks. MySQL is relational, so it can't take advantage of unstructured data the way MongoDB can. Also, the back-end (PHP/Perl/Python) and front-end (JavaScript/HTML) use different languages, making it harder for a developer to move fluidly between LAMP and a JavaScript-only stack like MEAN.

Real banking example

Capitec's own stack, given your syllabus, is heavily Java-centric — Spring Framework on the back end, React on the front end. That's neither MEAN/MEVN/MERN (all JavaScript-based) nor LAMP — it's its own combination, chosen presumably because Java + Spring gives the structure, type-safety, and maturity a regulated banking environment needs, which lighter JavaScript-only stacks don't prioritize as heavily.

Logic to hold onto

Every stack choice is really a trade-off between three things: how many languages you need to learn (MEAN's single-language JavaScript advantage), how mature and well-documented the ecosystem is (LAMP's age advantage), and how well it fits the specific type of data and scale you're working with (structured/relational vs unstructured, small app vs large-scale). There's no universally "best" stack — only a best fit for a given problem.
