Form-Based Security with Spring Security

What this lesson covers

Locking pages behind a custom login form, adding logout, and hashing passwords before they're saved to the database.

Real-life example: the Capitec app login. You type your details into the bank's own screen, and the bank never stores your actual PIN in readable form.

Acronyms in this lesson

  • IDE: Integrated Development Environment, like VS Code or IntelliJ.
  • JPA: Java Persistence API (Application Programming Interface), maps Java classes to database tables.
  • CSRF: Cross-Site Request Forgery, a fake request sent from another site using your logged-in session.

Step 1: Create the project

On start.spring.io choose Maven, Java, the latest stable Spring Boot, group com.example and artifact demo-security. Add Spring Web, Spring Security and Thymeleaf. For the password part you also need Spring Data JPA and a database driver like H2.

Step 2: SecurityConfig class

  • /public/** is open to everyone.
  • Every other request needs a login.
  • formLogin with loginPage("/login") uses your own login page, and permitAll() lets everyone see it.
  • logout() lets users sign out and ends their session.

Note: the video extends WebSecurityConfigurerAdapter. That class was removed in Spring Security 6 (Spring Boot 3), so the current way is a SecurityFilterChain bean.

Real-life example: the login page has to be permitAll, or users would need to log in to see the login page. Like locking the front door key inside the house.

Step 3: login.html

  • Form with method="post" and action pointing to /login.
  • Inputs named username and password, because those are the names Spring Security looks for.
  • A submit button.

Spring Security handles the POST to /login itself. You don't write a controller method for it, only a GET that shows the page.

Real-life example: you fill in the form, but the security guard at the door (Spring Security) does the actual checking, not the receptionist (your controller).

Step 4: Run and test

Run DemoSecurityApplication, go to http://localhost:8080, open a protected page and you get redirected to /login. Log in with a valid user.

Step 5: Password hashing

  1. Add the Spring Security dependency.
  2. Create a PasswordEncoder bean that returns BCryptPasswordEncoder.
  3. In the user service, call passwordEncoder.encode() before saving.
  4. Create a JPA entity with id, username and password.
  5. Register a user and check the database: the password should look like a random string starting with $2a$.

BCrypt "adapts over time" because you can raise its strength (work factor) as computers get faster. It's hashing, which is one-way, not encryption.

Real-life example: shredding a document and keeping only the shredded fingerprint. You can check if a new document matches, but nobody can rebuild the original.

Pseudocode: login flow


WHEN user opens a protected page
    IF not logged in
        redirect to /login

WHEN user submits login form
    Spring Security finds user by username
    hash the typed password and compare with stored hash
    IF match
        start session, send to the page they wanted
    ELSE
        redirect to /login?error

WHEN user clicks logout
    end session
    redirect to /login?logout

Pseudocode: registration


WHEN new user registers
    hashed = passwordEncoder.encode(plainPassword)
    create AppUser with username and hashed
    save AppUser to database

Tips for understanding the logic

  • Use th:action="@{/login}" in the form, not a plain action. Thymeleaf then adds the CSRF token automatically. Without it, the login gets blocked with 403.
  • Never compare passwords with equals(). Use passwordEncoder.matches(typed, stored), because the same password hashes differently each time.
  • I named the entity AppUser so it doesn't clash with Spring Security's own User class.
