Spring MVC Form Handling and Validation

What this lesson covers

How to capture data from an HTML form, bind it to a Java object, show it back to the user, and validate it before it gets processed. MVC stands for Model-View-Controller: the Model holds the data, the View is what the user sees, and the Controller handles requests and connects the two.

Example: a bank collects sign-up details from people at a sales conference and needs to load them into the client database without bad data getting in.

Step 1: Set up the project

Create a Spring Boot project with Spring Initializr. Add Spring Web (for controllers and HTTP), Thymeleaf (for HTML templates) and Validation (for the annotation rules).

Real-life example: like opening a new branch. You need the building (Spring Boot), the counter (Spring Web), the forms clients fill in (Thymeleaf) and the rules for checking them (Validation).

Step 2: Create the Model (User class)

A plain Java class with three fields: firstName, lastName and email. Getters and setters let Spring read and fill in the values.

Real-life example: the blank account opening form. It has boxes for each detail, but it is just a container for the data.

Step 3: Create the Controller

The class gets @Controller so Spring knows it handles web requests and returns view names.

  • showForm is mapped to GET /userForm. It puts an empty User in the model and returns the view name "userForm".
  • submitForm is mapped to POST /submitForm. @ModelAttribute binds the form fields into a User object. It adds the user to the model and returns "formResult".

Real-life example: the consultant hands you a blank form (GET), then takes it back once filled in and hands you a receipt (POST).

Step 4: Create the Thymeleaf templates

  • userForm.html: th:action points the form to /submitForm, th:object links it to the user object, and th:field connects each input to a User field.
  • formResult.html: th:text prints the submitted values.

Real-life example: th:field is like labelled boxes on a paper form. Each box only accepts the detail it is labelled for.

Step 5: Add validation to the Model

  • @NotEmpty: the field cannot be null or empty.
  • @Size: sets a minimum and maximum number of characters.
  • @Email: the value must look like a valid email address.

Each annotation has a message attribute, which is the error the user sees if the rule fails.

Real-life example: the rules printed at the bottom of a bank form, like "ID number must be 13 digits". The rules live with the form, not with the teller.

Step 6: Handle errors in the Controller

Put @Valid on the User parameter to trigger the checks. BindingResult must come straight after it and holds any errors. If bindingResult.hasErrors() is true, send the user back to userForm.

Real-life example: the consultant checks the form before capturing it. If something is missing, they hand it back and point at what to fix.

Step 7: Show errors in the form

Under each input, a div uses th:if with #fields.hasErrors('fieldName') to check for an error, and th:errors prints the message.

Real-life example: a red note next to the exact box you got wrong, instead of one vague "form invalid" stamp.

Pseudocode: full request flow


WHEN user opens /userForm
    create empty User
    put User in model
    show userForm page

WHEN user clicks Submit
    bind form fields into User
    run validation rules on User
    IF any rule fails
        show userForm again with error messages
    ELSE
        put User in model
        show formResult page

Tips for understanding the logic

  • Follow the URL. GET /userForm shows the form, POST /submitForm processes it. Find the matching method each time.
  • The string a controller method returns is the template file name without .html.
  • The name in th:object must match the model attribute name the controller added.
  • BindingResult must sit right after the @Valid parameter or Spring throws an error instead of returning to the form.

Testing

Run the app, go to http://localhost:8080/userForm, submit valid data to see the result page, then submit bad data (blank name, broken email) to check the error messages show next to the right fields.
