Spring Security Overview

What it is

Spring Security is the part of the Spring framework that handles who can get into an app and what they can do once inside. It also blocks common web attacks. A login page on its own isn't enough. The app also needs to stop forged requests, keep passwords unreadable, and limit access by role.

Real-life example: a bank branch doesn't just have a front door lock. It has ID checks, staff-only areas, a vault with limited access, and cameras.

Acronyms in this lesson

  • HTTP: HyperText Transfer Protocol, how browsers and servers talk.
  • XSS: Cross-Site Scripting, an attacker sneaks script code into a page so it runs in other users' browsers.
  • CSRF: Cross-Site Request Forgery, an attacker tricks a logged-in user's browser into sending a request they didn't mean to send.
  • RBAC: Role-Based Access Control, permissions are given to roles, and users get roles.
  • OAuth 2.0: Open Authorization, lets an app access things on your behalf without getting your password (like "Sign in with Google").
  • LDAP: Lightweight Directory Access Protocol, a company-wide directory of users and groups.
  • OIDC: OpenID Connect, sits on top of OAuth 2.0 and adds proof of who you are.
  • SSO: Single Sign-On, log in once and get into several systems.
  • URL: Uniform Resource Locator, a web address like /admin.

Authentication vs authorization

Authentication checks who you are (username and password checked against stored details). Authorization checks what you're allowed to do after that (admin vs normal user).

Real-life example: showing your ID at the branch is authentication. Being allowed into the vault only if you're a vault controller is authorization.

HTTP Basic authentication

The username and password are sent in an HTTP header with every request. Simple and fine for internal tools or APIs (Application Programming Interfaces), but it should always run over HTTPS so the details aren't readable in transit.

Real-life example: a staff-only internal tool that asks for your details each time you open it.

Form-based authentication

The user logs in through an HTML form. Spring Security gives a default login page, and you can swap in your own.

Real-life example: the Capitec app login screen.

Password storage and encoding

Passwords are never stored as plain text. BCryptPasswordEncoder turns a password into a hash that can't be turned back. At login, the typed password is hashed and compared with the stored hash.

Tip: the video calls this encryption, but BCrypt is really hashing. Encryption can be reversed with a key. Hashing is one-way.

Real-life example: like a fingerprint. You can match a finger to the print, but you can't rebuild the finger from the print.

CSRF protection

Spring Security gives each session a secret token that has to come back with every form submit. A forged request from another site won't have the token, so it gets blocked. It's on by default.

Real-life example: a one-time PIN (OTP) sent to your phone. A fraudster can fake the request but not the PIN.

Role-based access control

Permissions are tied to roles like ADMIN or USER, and users get roles. Spring Security checks the role before letting a request through.

Real-life example: tellers, branch managers and IT support each see different screens in the same banking system.

Integration with external systems

Spring Security can hand login off to LDAP, OAuth 2.0 or OIDC, which allows SSO across several apps.

Real-life example: logging into your work laptop once and then opening email, Teams and the intranet without logging in again.

How Spring Security enforces it

  • AuthenticationManager checks credentials, from memory, a database, LDAP or OAuth 2.0.
  • URL-level rules: lock whole paths, like /admin/**.
  • Method-level rules: @PreAuthorize or @Secured on a method.
  • httpBasic() and formLogin() switch on the two login styles.
  • BCryptPasswordEncoder hashes passwords.
  • CSRF tokens are created and checked automatically.

Pseudocode: what happens on each request


WHEN a request arrives
    IF the URL is public
        let it through
    ELSE IF user is not logged in
        send to login page (form) or ask for credentials (basic)
    ELSE
        IF user's role is allowed for this URL or method
            IF request changes data AND CSRF token is missing or wrong
                block it
            ELSE
                let it through
        ELSE
            return 403 Forbidden

WHEN user logs in
    hash the typed password
    compare with stored hash
    IF match, start a session
    ELSE show login error

Tips for understanding the logic

  • Spring Security works like a row of checkpoints (filters) that every request passes before it reaches your controller.
  • Read security rules top to bottom. The first rule that matches wins, so specific paths go before general ones.
  • 401 means "I don't know who you are". 403 means "I know who you are, but you're not allowed".
  • Roles in rules are written as "ADMIN", and Spring adds the "ROLE_" prefix behind the scenes.
