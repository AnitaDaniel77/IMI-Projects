Lab: Creating a Simple Web Page

IBM Web Development course, Module 1 hands-on lab. Built a fan page for Thomas J. Watson Sr. that uses most of the basic HTML building blocks on one page. Code is in web-11-code.html.

What the lab covers

One page, built top to bottom in the same order the browser reads it: document setup, title, heading, image, paragraph with a link, list, table, then a feedback form. Each piece is a separate element, and the finished page is just those pieces stacked.

The elements and what each one does

ElementJob on the page
DOCTYPETells the browser this is an HTML5 document, so it doesn't fall back to old rendering rules.
html, head, bodyhtml wraps everything. head holds information about the page (title). body holds what the visitor sees.
titleThe text on the browser tab. Also what search results show.
h1, h2Headings. h1 is the main one, h2 is a section under it.
imgShows a picture. src is where the file lives, width and height set the size, alt describes it in words.
p and aA paragraph, with a link inside it. href is the address the link goes to.
ul and liAn unordered (bullet) list. Each li is one bullet.
table, tr, th, tdA grid. tr is a row, th is a header cell, td is a data cell.
form, fieldset, legendThe form is the container. fieldset groups the fields and legend names the group.
label and inputThe label names a field. The input is where the visitor types. They connect through for and id.
textareaA multi-line box for longer text like comments.
buttonSends the form when type is submit.

Logic behind the page

The browser reads the file from the top and draws each element in order. Elements that sit inside others (li inside ul, td inside tr inside table) must be closed in the reverse order they were opened. If the nesting is wrong, the browser guesses, and the page can look broken without any error message.

The form works in two stages. First the browser checks the rules on the fields (required, email format) before anything leaves the computer. Only if every rule passes does it package the field values by their name attributes and send them to the address in action, using the method.

Pseudocode

START page
    declare document type as HTML5
    OPEN html
        OPEN head
            set tab title to "Thomas J. Watson Sr - Fan Page"
        CLOSE head
        OPEN body
            show main heading "Thomas J. Watson"
            show image from the web address, 300 x 300, with a text description
            show paragraph about Watson
                inside the paragraph, make "IBM" a link to ibm.com
            show bullet list of 4 facts
            show main heading "IBM Growth Over Years"
            show table
                header row: Year, Employees, Gross Income
                FOR each of 3 years (1925, 1930, 1935)
                    add a row with the year, employees and income
            show section heading "Insights Submission Form"
            OPEN form (send to /submit-feedback using POST)
                group fields under the legend
                name field: text, required
                email field: email format, required
                comments field: multi-line, optional
                submit button
            CLOSE form
        CLOSE body
    CLOSE html
END page

ON submit clicked
    IF name is empty OR email is empty OR email format is wrong
        stop and show the browser's message
    ELSE
        send name, email, comments to /submit-feedback

Real-life banking example

Think of the Capitec app's "contact us" screen. The heading is the screen title. The table is like a statement: header row with Date, Description, Amount, then one row per transaction. The bullet list is the list of things you can do on that screen, where the order doesn't matter. The feedback form is the complaint form: name and email are required because the bank can't reply without them, and the comments box is optional because some people only want to be called back.

The email check matters in banking for the same reason. A typo like "anita@gmail" bounces, and the customer never hears back. The browser catching that before submit saves a wasted request.

Tips for understanding the logic

Read the page like a document outline. If you removed all the tags, would the order of content still make sense? If yes, the structure is sound.

Use th for column titles and td for data, even if both look the same. Screen readers announce th as a header, which is how a blind customer would know which column a number belongs to.

The label's for must match the input's id exactly. When it does, clicking the label puts the cursor in the field. It's the quickest way to test you wired it correctly.

The name attribute on an input is what the server receives. Without it, the field shows on screen but its value is never sent.

The lab used two h1 elements. That works, but one h1 per page with h2 for sections is the better habit, and it's worth switching to when you build your own pages.

Things I noticed

The lab left alt off the image, so I added it. Without alt, a broken link shows nothing and a screen reader says nothing.

Live Server only serves files. It has no code listening at /submit-feedback, so submitting the form fails locally. Handling that route is back-end work (in Java, a Spring controller), which is where this course eventually leads.
