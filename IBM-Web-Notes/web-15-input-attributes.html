HTML5 Input Element Attributes

IBM HTML, CSS and JavaScript course, Module 2 lecture. Code is in web-15-code.html and web-15-code.js.

What the lecture covers

The input tag changes what it does based on its type attribute. HTML5 added new types (color, date, datetime-local, email, number, range, search, tel, url) and new attributes (list, placeholder, required). Used well, the browser does a lot of the checking for you before the form is ever sent. The lecture ends on what to do when a browser does not support these features: validation fallback.

The attributes

The list attribute links an input to a datalist, which holds option entries. The options are only suggestions, so it works as auto-complete and the user can still type something else. This is different from a select dropdown, where the user must pick one of the choices.

The placeholder attribute shows a faint example of the format inside an empty box. It is a hint only. If the user leaves the box alone, the placeholder text is not sent with the form.

The required attribute means the user must type something before the form can be sent. A placeholder does not count as typed text, so a field with a placeholder and the required attribute still blocks the form.

Real-life example: on a branch deposit slip, the printed hint "e.g. 0821234567" in light grey is the placeholder. The red asterisk next to a box that cannot stay empty is required. The branch name that auto-completes as you type is the datalist.

Validation fallback

Not every browser supports every HTML5 input feature. If the browser does not understand a type, it shows a plain text box instead, so the checking never happens. Three ways to cover this, in the lecture:

  • Use JavaScript or a library such as jQuery to add the checks.
  • Assume browsers will catch up and leave final validation to the server.
  • Attach a validation function to the form's submit event, so every field is checked at the moment of sending.

Real-life example: the teller at the branch checks your ID in person (browser check), but the bank's back office checks it again before the account opens (server check). You never rely on only one of them, because the browser check can be skipped or faked.

Logic

Choose the most specific type for each field. That gives the user the right keyboard or picker for free and gives the browser something to validate. Add required to the fields that cannot be empty and a placeholder to show the format. Then add a JavaScript check on submit as a safety net, and treat the server as the final authority.

Pseudocode

START form
    FOR each field
        choose the input type that matches the data
            colour, date, date and time, email, number, slider, search, phone, web address
        add a hint (placeholder) showing the format
        IF the field cannot be empty
            mark it required
    branch field gets a list of suggestions (datalist)
    slider shows no number by itself
        ON slider move
            copy the slider value into a label next to it
END form

ON form submit
    stop the form from being sent
    problems = empty list
    IF email has no "@" or no "."
        add "email looks wrong" to problems
    IF phone is not 10 digits starting with 0
        add "phone must be 10 digits" to problems
    IF problems is empty
        show "all good"
    ELSE
        show all the problems

Tips for understanding the logic

  • If a new input type shows as a plain text box in a browser, that is the fallback in action. Nothing is broken.
  • Type "abc" into the email box and press submit. If the browser complains before your own code runs, native validation is working.
  • Number checks the value is a number. Pattern checks the shape of text. Use pattern with tel, because tel on its own checks nothing.
  • The placeholder is not a value. If the box looks filled but required still stops you, that is why.
  • Never trust only the browser. A user can switch off JavaScript or send the data directly, so the server must validate too.
