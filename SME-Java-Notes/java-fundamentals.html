2. Live coding - starting from a blank App.java

public class App {
    public static void main(String[] args) throws Exception {
        // "static" here means the JVM can call main() without
        // first creating an App object - it's the front door.
        Integer numberOfStudents = 5;

        if (numberOfStudents == 5) {
            StartLecture(); // only fires once the class is full
        }
    }

    private static void StartLecture() {
        // private = only App itself can call this.
        // Real-life parallel: a receptionist who only the
        // front desk staff can page, not the public.
        return;
    }
}

Real-life example: think of main as the front door of a building - everything starts there. numberOfStudents == 5 is like a bouncer checking if the room hit capacity before letting the "lecture start" announcement go out.

3. Growing the example into a mini domain model

var session = new Session();               // a new classroom, empty for now
var student = new Person(name: "Hilbert");  // a person walks in
var lecturer = new Lecturer(string: "Lecturer1");

student.JoinSession(session.Id);
// student doesn't carry the whole Session object around -
// just its ID. Real-life parallel: you don't carry the whole
// classroom with you, you just remember the room number.

if (session.GetStudentCount() == 5) {
    // ask the session itself how full it is, rather than
    // trying to count from outside
    lecturer.StartLecture();
}

Hilbert's own explanation, paraphrased: a test student joins a session by passing in the session ID, the session reports back its student count, and once that hits five, the lecturer gets triggered to start - deliberately made a bit more complex than needed, just to make the example richer.

4. Person.java - evolving step by step

First pass

public class Person {
    private String name;  // private = nobody outside this
    private String role;  // class can touch these directly

    public Person(String name, String role) {
        this.role = role; // "this.role" = the field,
        this.name = name; // "role" = the parameter - this
                           // is how Java tells them apart
    }

    public String getName() {
        return name; // the only door in to read the name
    }
}

Real-life example: private fields are like a diary with a lock - getName() is the one page you're allowed to show people.

Second pass - overloaded constructor, default value

private String role = "Student"; // default if nothing's passed in

public Person(String name) {
    this.name = name; // shorter constructor - role stays "Student"
}

public String getRole() {
    return role;
}

public String updateRole(String newRole) {
    this.role = newRole;
    return this.role; // hands back the new role so the
                       // caller gets confirmation immediately
}

Real-life example: it's like signing up for a gym with no membership type specified - you default to "Basic" until you upgrade.

Third pass - role becomes an Enum, backed by a new Roles.java

private Enum role; // now locked to a fixed list of options

public Person(String name, Enum role) {
    this.role = role;
    this.name = name;
}

public String updateRole(Enum newRole) {
    this.role = newRole;
    return this.role;
}

Used in App.java:

var student = new Person(name: "Hilbert", Roles.STUDENT); // correct - enum
var lecturer = new Person(name: "Jane", role: "Lecturuer"); // typo! still
// String-based, so Java lets it through silently - this is
// exactly the bug the enum switch was meant to prevent.

Real-life example: a String role is like writing your job title on a sticky note - anyone can misspell it and no one notices. An Enum is like a dropdown menu on a form - you can only pick from what's actually there, so "Lecturuer" wouldn't even be an option.

5. Java Platform

  • Built around the JVM - the most common scenario
  • Compiles to bytecode rather than native code
  • Just-in-time (JIT) compilation gives native-level performance
  • Runs anywhere there's a JVM - platform independence
  • Native executable binaries are an option too (platform-specific, fast startup, low resource use)

Real-life example: bytecode + JVM is like a universal power adapter - you write the code once, and the JVM on each machine "translates" it to run there, instead of you needing a different plug for every country.

6. Community Driven

  • Open source (OpenJDK)
  • Java Community Process
  • Technology Compatibility Kit (TCK)
  • Early access / interim versions

7. Java Development Kit (JDK)

Includes the JRE (runs programs), the compiler javac (turns source into bytecode), and tools like javadoc, jar, jdb.

Think of it as: a carpenter's toolbox - everything needed to build Java applications.

8. Java Community Process (JCP)

Companies, experts, open-source contributors, and Oracle propose changes as JSRs (Java Specification Requests) to evolve the language together.

Think of it as: a committee that decides how Java should evolve.

9. Technology Compatibility Kit (TCK)

A test suite any Java implementation must pass to be considered "Java compatible," protecting the "Write Once, Run Anywhere" promise.

Think of it as: the final exam proving an implementation follows the official rules.
