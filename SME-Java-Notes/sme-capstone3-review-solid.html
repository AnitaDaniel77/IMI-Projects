SME Session 19 Nov 2026: Capstone 3 Review and SOLID

Led by Hilbert Muchatibaya. He reviewed where the cohort lost marks on Capstone 3 and tied the fixes back to the SOLID principles.

Acronyms

  • SOLID: five design principles. S = Single Responsibility, O = Open/Closed, L = Liskov Substitution, I = Interface Segregation, D = Dependency Inversion.
  • EFT: Electronic Funds Transfer, a bank-to-bank payment.
  • BNPL: Buy Now Pay Later.
  • DI: Dependency Injection, where something else hands your class the objects it needs instead of the class creating them.
  • POM: Project Object Model, the Maven pom.xml file.

What the brief asked for

  • A PaymentMethod interface with processPayment(double) and getPaymentType().
  • At least three rails: Card, EFT and Wallet, each printing which rail runs.
  • One checkout path that takes a PaymentMethod, never a concrete class.
  • The total is worked out from the order lines and passed to the rail.
  • On success, print the rail, the amount and "order complete".
  • PaymentProcessor works with any PaymentMethod.

The test the brief gives you: adding BuyNowPayLaterPayment should only need one new class plus wiring in the demo, and the order maths must not change.

Polymorphism: code talks to a contract (PaymentMethod) and works with any class that signs it, without knowing which one it got.

Real-life example: a card machine accepts Visa, Mastercard or Amex. The shop doesn't need a different till for each one.

Where marks were lost

Code and design

  • Rails with no rule of their own, where every rail just returns true.
  • No tests for the failure path, and no tests of the console output.
  • "Order complete" missing on success, or printed on failure.
  • The same amount check repeated in every rail.
  • Money stored as double, with no care at the boundary.
  • The total calculated in two places (Order and a summary).
  • README missing the reasoning for using an interface.

Build and brief

  • Maven Surefire (the plugin that runs tests) not configured, so no proof the tests ran.
  • pom.xml not set to Java 21.
  • The compiled target/ folder committed to Git. It belongs in .gitignore.
  • PaymentMethod written as an abstract class when the brief says interface.

Real-life example: these are the small things an auditor flags, like a missing signature or the wrong form version. The work is fine, but the brief wasn't followed exactly.

Each rail owns a business rule

  • Card: a limit per payment.
  • EFT: needs a bank reference.
  • Wallet: can't spend more than the balance.
  • BNPL: a credit limit.

Decline, don't throw. A decline is a normal answer, so return false and leave the balance untouched. Don't throw an exception for "balance too low".

Real-life example: when your card is declined at a till, the till doesn't crash. It just says "declined" and you try another card.

O: Open/Closed Principle

A class should be open for extension but closed for modification. In Hilbert's code, processPayment is final in the parent. It runs the shared amount check once, then calls doProcess, which each rail overrides. Adding a rail never touches the tested parent.

Legacy code is code that's been in production a long time, often written by someone who has since left. Changing it means you don't know the full impact, so you'd need full regression testing (retesting everything). Extending it means testers only test the new rail.

Real-life example: adding a new branch to a bank doesn't mean rebuilding head office. The new branch follows the same rules and plugs into the same system.

I: Interface Segregation Principle

Keep interfaces small and specific. Not every rail can do tap to pay, so tap to pay gets its own small interface, and only rails that support it implement it. The same goes for Refundable.

Real-life example: not every client gets a credit card. A savings account doesn't come with a credit limit just because some accounts have one.

D: Dependency Inversion Principle

Depend on abstractions (interfaces), not concrete classes. Writing new CardPayment() inside main is a hard dependency. Every "new" tells Java to build that object right now, so if it's broken, the whole app can fail to start.

A dependency injection container holds all the rails. When a user picks "Wallet", the app asks the container for the wallet rail. If one rail can't be found, you show a clear message like "failed to resolve card" and the rest of the app keeps working. Spring's constructor injection does this for you (to be covered later).

Redundancy works on the same idea: two routers on different networks (say MTN and another provider), so if one fails, traffic switches to the other. No single point of failure.

Real-life example: a branch that only has one teller who can open accounts stops opening accounts when she's off sick. If any trained consultant can be called on, the work carries on.

Value objects

A value object has no id, can't be changed, and two of them are equal if their values match. An email is just a String until it follows the email format. Money only makes sense as a currency plus an amount. Value objects belong in the domain layer.

Real-life example: two R100 notes are the same value. You don't care which one you get. An account is different, because its account number makes it unique (an entity).

Entities and the shared folder (to expand later)

  • Product, Order and Customer are entities, because each has an id. A parent Entity class can hold what they share, and each one extends it.
  • A shared folder holds helpers every layer needs, like formatting phone numbers.

Pseudocode: payment flow after the fixes


SETUP (one place only)
    register Card, EFT, Wallet, BNPL rails in the resolver

CHECKOUT(selection, orderTotal)
    method = resolver.resolve(selection)
    IF method not found
        print "failed to resolve"
        STOP
    paid = method.processPayment(orderTotal)
        parent: IF amount not above 0 -> reject, return false
        rail:   apply own rule (limit / reference / balance / credit)
                IF rule fails -> print decline, return false
                ELSE -> take payment, return true
    IF paid
        print rail, amount, "order complete"
    ELSE
        print rail, amount, "payment failed"

Tips for understanding the logic

  • Find the word "final" on processPayment. That one keyword is what stops a rail from skipping the shared check.
  • Search for "new" in the checkout code. If you find a concrete rail there, that's a hard dependency.
  • For every rail, ask what makes it say no. If the answer is "nothing", it needs a rule.
  • Test both paths: one success and one decline per rail, and check what gets printed.
  • The brief's test is the best check: can you add BNPL with one new class and no edits elsewhere?
