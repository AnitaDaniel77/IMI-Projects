SME Session 26 Nov 2026: Capstone 4 Prep

Led by Hilbert Muchatibaya. Topic: smart rail selection and transaction risk, using the strategy pattern.

Acronyms

  • EFT: Electronic Funds Transfer, a bank-to-bank payment.
  • RTGS: Real-Time Gross Settlement, a rail for very large payments that settle immediately.
  • BNPL: Buy Now Pay Later.
  • DRY: Don't Repeat Yourself.
  • SOLID: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.
  • AWS: Amazon Web Services, a cloud provider.

Where we are

  • Capstone 3 answered HOW we pay: one PaymentMethod contract, many rails (card, EFT, wallet). Each rail owns a rule and a decline returns false.
  • Capstone 4 adds a layer above that: choosing the provider. It continues in your own Capstone 3 repo, where you add the routing skeleton.

Real-life example: Capstone 3 built the tills. Capstone 4 adds the floor manager who tells each client which till to go to.

The three new questions for every payment

  1. Which provider should process it, for this amount and bank?
  2. What risk level applies before the money moves?
  3. Why was that decision taken? It must be traceable.

Smart rail selection

Based on things like the amount, the origin and the destination, the system offers a better rail, for example EFT instead of wallet, or BNPL. Done well, the merchant pays lower fees and the platform makes more profit.

Real-life example: a navigation app with one car and one destination, but you choose fastest, shortest or avoid tolls. The app has a route strategy and hands the calculation to it.

Transaction risk

Rules score or block a transaction. For example, a large amount from a certain origin with no ID provided gets blocked. Check the risk work in the safe pay repository from about a month ago.

Fraud score idea: 0 to 5, one point per check passed (who you are, card details and so on). A score of 4 or more unlocks certain rails. The report can be built step by step with the Builder pattern, adding each check as it passes.

Real-life example: opening an account. Each document you bring ticks a box, and only with enough ticks can you get a credit card.

The strategy pattern

  • Put each way of deciding behind an interface.
  • Swap the decision without changing the code that uses it.
  • You've done this already: PaymentMethod is a strategy for how to pay.
  • Capstone 4 uses it again: each routing rule is one way of deciding.

The four parts (GeeksforGeeks sorting example):

  • Client: asks for the work (main, or an API request).
  • Context: holds a strategy and hands the work to it (SortingContext, PaymentRailSelector).
  • Strategy interface: the contract (SortingStrategy, PaymentRailStrategy).
  • Concrete strategies: the real implementations (BubbleSort, QuickSort, MergeSort, or Wallet, Card, EFT, RTGS).

How it all fits together

  • Interface: the contract every strategy honours. PaymentMethod in Capstone 3, RoutingRule now.
  • Polymorphism: the same call, different behaviour. The calling code never changes.
  • Inheritance: "is-a", sharing code through a parent class. Strategies don't need it.
  • Strategy: the engine HAS a swappable strategy, so you change behaviour without rewriting the engine.

Hilbert's demo: amount bands

  • Wallet: up to R500
  • Card: above R500 up to R10,000
  • EFT: above R10,000 up to R100,000
  • RTGS: above R100,000

The selector loops through the list and takes the first rail whose supports() is true, so the list order is the priority. If nothing matches, it throws. His suggested upgrade is to check every option and take the one with the lowest risk. The bands in his demo don't overlap, but once you add rules on the user or the bank, they can, and then you need a tie-break.

Design question he left for the cohort: does supports() live on the PaymentMethod parent, or on each rail? Each rail may apply its rules differently, so he leans towards each rail owning its own.

Orchestrator: microservice vs monolith

  • Microservice: the orchestrator is a separate project in front, like a traffic controller, sending each payment to the BNPL, crypto, EFT, card or wallet service.
  • Monolith: one application holds everything. PayNest is a monolith.

Other principles

  • DRY: if you copy-paste the same logic twice, move it into a base class or helper method.
  • Capability interfaces: BankSettlement (settlementTime, getBankReference) is only implemented by EFT. Interface Segregation again.
  • Single Responsibility scales beyond Java: no service that does 20 things.
  • Failover and redundancy: don't tie yourself to one provider. The AWS and Microsoft outages took businesses down, so build a fallback.
  • Architecture comes before prompting AI tools. You still make the design decisions.

Advice for the capstone

  • Read the brief for the small requirements, the "nooks and crannies".
  • Do exactly what the rubric asks. Build extra ideas separately and send them to Hilbert directly.
  • Concepts (SOLID, DRY, clean architecture) matter more than any one language, but submit Java for marks.
  • In interviews, knowing how a system works matters more than remembering an exception's name.

Pseudocode: routing a payment


CREATE order (reject if id blank or amount not above 0)
BUILD fraud report: add one point per check passed

FIRST MATCH
    FOR each rail in priority order
        IF rail supports order and score
            RETURN decision(rail, "first match")
    RETURN decision(NONE, "no rail supports")

LOWEST RISK
    best = none
    FOR each rail
        IF rail supports order and score
            IF best is none OR rail risk lower than best risk
                best = rail
    RETURN decision(best, "lowest risk") or NONE

PAY on the chosen rail, keep the decision as the trace

Tips for understanding the logic

  • Find the context (the selector). It never names a specific rail, it only loops over the interface.
  • Adding a rail should mean one new class and one line in the list. If you edit the selector, Open/Closed is broken.
  • Ask "what if two rules match?" and "what if none match?" for every design.
  • The RoutingDecision record is your answer to "why was that decision taken?".

Update from Hilbert (27 Nov email)

  • Wallet vs EFT was only an example of the strategy pattern.
  • Capstone 4: RoutingRule classes evaluate a Transaction, and the routing engine selects a provider. Keep routing rules separate from payment methods.
  • Transaction only has amount, bank and timestamp. No location fields or merchant-specific rules.
